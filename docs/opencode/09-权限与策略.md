# 09 权限与策略

> 来源：官方 `permissions`、`policies`、`migrate-v1`、`openapi.json`（`/api/permission*`、`/api/session/{id}/permission*`）。
> 这两个概念经常被混淆：**permissions 是每 Agent 的可提示规则，policies 是不可提示的强制约束**。

## 1. 一张表看清区别

| 维度 | `permissions` | `policies` |
|---|---|---|
| 目的 | 控制 Agent 能否对某资源执行某动作 | 强制禁止/放开某类能力 |
| 取值 | `allow` / `ask` / `deny` | `allow` / `deny` |
| 是否提示 | `ask` 会等待客户端决策 | 从不提示 |
| 能否放宽 | 可以 | 只能收紧（`allow` 只用于解除更宽的 deny） |
| 配置位置 | 顶层 + `agents.<id>.permissions` + 会话级 | 顶层 + `experimental.policies`（兼容）+ Console |
| 求值顺序 | 从低优先级到高优先级，**最后匹配者生效** | 越宽泛越晚求值，**托管/系统/Console 覆盖项目** |
| 典型用途 | “shell 需审批”“禁止编辑 *.env” | “禁止使用 openai”“禁止 shell:git push” |

一句话：**permissions 决定“要不要问人”，policies 决定“无论谁同意都不行”**。

## 2. `permissions` 规则

### 2.1 结构

每条规则三个字符串字段：

```jsonc
{
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status *", "effect": "allow" },
    { "action": "shell", "resource": "git diff *", "effect": "allow" },
    { "action": "shell", "resource": "git push *", "effect": "deny" }
  ]
}
```

| 字段 | 含义 |
|---|---|
| `action` | 工具权限动作（见 2.3） |
| `resource` | 被使用的值：路径、命令、URL、查询、技能 ID、Agent ID 等 |
| `effect` | `allow` / `deny` / `ask` |

- 没有规则匹配时，默认 **`ask`**。
- 但基础策略（见 2.4）包含 `*/* → allow`，所以实际默认是“允许”，除了显式 ask 的项。

### 2.2 匹配规则

简单整值通配符：

| 模式 | 匹配 |
|---|---|
| `*` | 零或多个字符，**包括 `/`** |
| `?` | 恰好一个字符 |
| 其他 | 字面字符 |

- 匹配整个规范化路径；反斜杠转 `/`；Windows 上大小写不敏感。
- shell 规则以 ` *` 结尾时，也匹配不带参数的命令：`git status *` 匹配 `git status` 与 `git status --short`。
- 规则按顺序合并，**最后匹配者生效**：低优先级配置先加载，全局规则追加，Agent 规则最后追加。

多资源操作：

```text
任一 deny → 整体 deny
否则任一 ask → ask
否则 allow
```

### 2.3 内置 action 与 resource

| action | resource |
|---|---|
| `read` | Location 相对内部路径，或规范化后的绝对外部路径 |
| `edit` | `edit`/`write`/`patch` 的目标路径 |
| `glob` | 请求的 glob pattern |
| `grep` | 请求的正则（**不是**搜索路径） |
| `shell` | scanner 产出的命令字符串；复合命令可能多条 |
| `subagent` | 目标 Agent ID |
| `skill` | 技能 ID |
| `question` | `*` |
| `webfetch` | 请求的 URL |
| `websearch` | 搜索查询 |
| `experimental_image_generate` | 选中的图片模型 `providerID/modelID[#variant]` |
| `external_directory` | 规范化的外部目录边界，通常以 `/*` 结尾 |
| `<server>_<tool>` | MCP 工具；`*` 为 resource |
| `opencode_list_mcp_resources` | MCP server 名 |
| `opencode_read_mcp_resource` | `<server>:<uri>` |
| `execute` | `*`；deny 会移除 Code Mode 及其专属工具，嵌套工具仍各自检查 |

`doom_loop` 与 `lsp` **不是** V2 Core 的权限 action。

V2 的 action 是字符串，插件可以定义更多 action。

### 2.4 默认基础策略

每个 Agent（包括自定义 Agent）都从以下有序基础策略开始：

```jsonc
[
  { "action": "*", "resource": "*", "effect": "allow" },
  { "action": "read", "resource": "*.env", "effect": "ask" },
  { "action": "read", "resource": "*.env.*", "effect": "ask" },
  { "action": "read", "resource": "*.env.example", "effect": "allow" }
]
```

内置 Agent 追加：

| Agent | 追加策略 |
|---|---|
| `build` | 允许提问 |
| `plan` | 允许提问；除 `~/.opencode/plan` 下的文件外，拒绝编辑 |
| `general` | 拒绝提问与启动子 Agent |
| `explore` | 除 shell、read、glob、grep、webfetch、websearch、external_directory 外全部拒绝；`.env` 读取需 ask |
| `title` | 拒绝所有动作 |
| `summary` | 拒绝所有动作 |
| `compaction` | 保持基础策略 |

**注意**：默认没有 `external_directory` 的 ask/deny 规则，所以 Location 与 worktree 之外的读写**不会提示**。这与 V1 不同。要恢复 V1 行为：

```jsonc
{ "permissions": [ { "action": "external_directory", "resource": "*", "effect": "ask" } ] }
```

### 2.5 外部目录

路径同时不在活动 Location 与其非根项目 worktree 内时，先检查 `external_directory`，再检查 `read`/`edit`。

```jsonc
{
  "permissions": [
    { "action": "external_directory", "resource": "~/projects/reference/*", "effect": "allow" },
    { "action": "read", "resource": "~/projects/reference/*", "effect": "allow" },
    { "action": "edit", "resource": "~/projects/reference/*", "effect": "deny" }
  ]
}
```

- 对 `external_directory`、`read`、`edit`，配置加载时会展开开头的 `~`、`~/`、`$HOME`、`$HOME/`。
- shell 的 resource 是原始命令文本，**不**做 home 展开。
- 相对修改路径可以离开活动 Location 但仍在项目 worktree 内。
- 显式外部路径会先规范化，再匹配；只授权可信目录边界。

### 2.6 Agent 级规则

```jsonc
{
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status *", "effect": "allow" }
  ],
  "agents": {
    "reviewer": {
      "description": "Review code without changing it",
      "mode": "subagent",
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" }
      ]
    }
  }
}
```

- Agent 规则**追加**在全局规则之后，不替换全局数组。
- 自定义子 Agent 使用自己的权限，不是父 Agent 的子集。
- 会话级 `permissions`（创建会话时传入）同样追加在最后。

### 2.7 审批流程

`ask` 时客户端可回复：

| 选择 | reply | 结果 |
|---|---|---|
| Allow once | `once` | 只批准当前请求 |
| Allow always | `always` | 批准，并保存工具建议的 pattern 到项目 |
| Reject | `reject` | 拒绝，并拒绝该会话中**所有其他待处理**权限请求 |

- `always` 保存的是**持久的、项目级** `allow` 规则，不会覆盖配置中的 `deny`。
- 工具决定建议的 pattern：有的建议 `*`，shell 建议命令前缀，skill/subagent 建议其 ID。
- 被拒绝时可以附带反馈文本；非交互客户端必须自行决定如何处理审批。
- 已保存审批可通过 `GET /api/permission/saved` 查看，`PATCH`/`DELETE` 修改。

### 2.8 Shell scanner

- 覆盖 Bash、Zsh、POSIX `sh`、PowerShell。
- 语法错误或无法安全分析的动态求值 → 返回 scanner error，不执行未验证子命令。
- 规则、已保存审批、best-effort 目录推断会应用到每条提取出的子命令与 `cd` 目标。
- 没有额外的“未知目录审批模式”或“一刀切限制”；需要时自己加 `shell`/`external_directory` 规则。

**警告**：`shell` 以宿主用户权限运行，目录推断是 best-effort。应优先使用窄 allowlist，而不是试图用 pattern 识别所有危险命令。

## 3. `policies` 语句

### 3.1 结构

```jsonc
{
  "policies": [
    { "action": "provider.use", "resource": "openai", "effect": "deny" }
  ]
}
```

| 字段 | 值 | 含义 |
|---|---|---|
| `action` | `provider.use`、`tool.use`、`integration.connect`、`integration.use`、`mcp.use`、`skill.use`、`plugin.use`、`websearch.use` | 被控制的操作 |
| `resource` | 字符串或通配符 | 具体对象 |
| `effect` | `allow` / `deny` | 匹配时的决定 |

- 校验失败的语句会被丢弃并在 server 日志中警告，其余语句继续生效。
- `experimental.policies` 仍可用，并合并进 `policies`。

### 3.2 匹配与顺序

- 与 permissions 相同的整值通配符：`*` 零或多字符，`?` 一个字符。
- 以 ` *` 结尾的 pattern 也匹配不带参数的值：`shell:git push *` 覆盖 `git push`。
- 多条匹配时**最后一条生效**；没有 specificity 规则。
- 因此：**宽泛语句在前，例外在后**。
- 没有匹配时默认 **allow**。

```jsonc
{
  "policies": [
    { "action": "provider.use", "resource": "*", "effect": "deny" },
    { "action": "provider.use", "resource": "anthropic", "effect": "allow" }
  ]
}
```

只保留 Anthropic。

### 3.3 `provider.use`

- 控制 provider 是否**可用**；resource 是 provider ID。
- 被拒绝的 provider 即使有有效凭据也会从目录与模型选择中消失。
- 适用于目录数据、环境变量、保存的账号、内置插件、配置文件等所有来源。
- 替代 V1 的 `enabled_providers` / `disabled_providers`。

### 3.4 `tool.use`

- 在权限检查之后**硬拒绝**；resource 是 `<action>:<value>`，匹配工具检查的每个资源。
- 被拒绝时返回 `Blocked by configuration policy`，不弹提示。
- 在 Agent 规则与已保存审批之后执行，因此能覆盖 `ask` 与 `always`。

```jsonc
{
  "policies": [
    { "action": "tool.use", "resource": "shell:git push *", "effect": "deny" },
    { "action": "tool.use", "resource": "edit:*.env", "effect": "deny" },
    { "action": "tool.use", "resource": "webfetch:*", "effect": "deny" }
  ]
}
```

| pattern | 阻断 |
|---|---|
| `shell:*` | 所有 shell 命令 |
| `read:*/.ssh/*` | 读 SSH 材料 |
| `external_directory:*` | 任何 Location/worktree 之外的访问 |
| `subagent:general` | 启动某个子 Agent |
| `github_delete_repository:*` | 某个 MCP 工具 |
| `*` | 所有尚未被拒绝的 |

`tool.use` 的 `allow` **不会授予**访问，只能解除更早的宽泛 deny；之后仍由 Agent 规则决定。

### 3.5 integration

integration 是 `/connect` 中连接的东西：Console（`opencode`）、provider（`anthropic`）、搜索服务（`exa`）、well-known 配置源（`https://ai.acme.com`）等。

| action | resource | 作用 |
|---|---|---|
| `integration.connect` | integration ID | `/connect` 列出/可连接哪些集成 |
| `integration.use` | `<integration>#<account>` 或裸 ID | 该集成提供的 provider/模型/搜索/MCP/配置 |

- 未连接账号时 resource 是裸 ID：免费层 `opencode`、`ANTHROPIC_API_KEY` 是 `anthropic`、配置中的 provider 是其 ID。
- 登录 MCP server 不受 integration 策略影响，用 `mcp.use`。

MDM 示例（只允许一个 Console workspace）：

```jsonc
{
  "policies": [
    { "action": "integration.connect", "resource": "*", "effect": "deny" },
    { "action": "integration.connect", "resource": "opencode", "effect": "allow" },
    { "action": "integration.use", "resource": "*", "effect": "deny" },
    { "action": "integration.use", "resource": "opencode#org_01M3...", "effect": "allow" }
  ]
}
```

### 3.6 MCP / skill / plugin

| action | resource |
|---|---|
| `mcp.use` | 配置中的 MCP server 名 |
| `skill.use` | 技能 ID |
| `plugin.use` | 无版本包名或绝对路径 |

```jsonc
{
  "policies": [
    { "action": "mcp.use", "resource": "*", "effect": "deny" },
    { "action": "mcp.use", "resource": "github", "effect": "allow" },
    { "action": "plugin.use", "resource": "opencode-acme-cli", "effect": "deny" }
  ]
}
```

被拒绝的 MCP server/skill 会被移除，被拒绝的 plugin 不会加载。

**2.2.3 升级提示**：旧版 `integration.use` 通过 `mcp:`/`skill:`/`plugin:` 前缀覆盖这三类。带前缀的语句仍会加载并转换；不带前缀的语句（包括裸 `*`）现在只作用于 integration。旧的宽泛 deny 需要拆成三条。

### 3.7 `websearch.use`

- 控制 `websearch` 工具可用的搜索 Provider；resource 是 Provider ID。
- 被拒绝的 Provider 即使无需 API key（如 Exa、TinyFish）也会被移除。
- 全部被拒绝时，`websearch` 工具不再提供。
- 2.2.6 之前的客户端忽略该 action。

### 3.8 优先级

普通配置“就近覆盖”，**policies 相反**：越宽泛的配置越晚求值，因此覆盖更窄的配置。

| 优先级 | 来源 |
|---|---|
| 1（最高） | macOS managed preferences（`ai.opencode.managed.plist`） |
| 2 | 系统 `opencode.json(c)`（`/etc/opencode` 等） |
| 3 | 已连接的 OpenCode Console workspace |
| 4 | 全局 `~/.config/opencode/opencode.json(c)` |
| 5 | 直接 `opencode.json(c)`；外层目录覆盖内层 |
| 6（最低） | `.opencode/opencode.json(c)`；外层目录覆盖内层 |

- 同一文件内保持书写顺序；最后匹配者生效。
- 仓库不能重新启用全局 deny 的 provider。
- Console 策略约每分钟拉取一次；切换 workspace 会替换语句；断开连接会清除；Console 不可达时保留最后一次语句。
- Console 与 policy 插件不能被 `plugins` 配置禁用。

### 3.9 限制

- policies **不配置** endpoint 或凭据，也不能让不可用的 provider 变可用。
- policies **不沙箱化插件代码**；被拒绝的 provider 是在正常 provider/model 路径上被阻断。
- 只能收紧，`allow` 只用于解除更宽的 deny。

## 4. 权限相关 HTTP API

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/permission/request` | 全局待处理请求（可 `location` 过滤） |
| `GET` | `/api/permission/saved` | 已保存的项目级 allow 规则 |
| `PATCH` | `/api/permission/saved/{id}` | 修改已保存规则 |
| `DELETE` | `/api/permission/saved/{id}` | 删除已保存规则 |
| `POST` | `/api/session/{sessionID}/permission` | 创建权限请求（客户端/插件） |
| `GET` | `/api/session/{sessionID}/permission` | 列出会话请求 |
| `GET` | `/api/session/{sessionID}/permission/{requestID}` | 单条 |
| `POST` | `/api/session/{sessionID}/permission/{requestID}/reply` | `{ decision, message? }` |

`decision` 取值：`once` / `always` / `reject`。

事件：

| 事件 | payload 要点 |
|---|---|
| `permission.asked` | `id`、`sessionID`、`action`、`resources[]`、`save[]`、`metadata`、`source`、`message` |
| `permission.replied` | `sessionID`、`requestID`、`reply` |

## 5. 控制面关注点

- **审批 UI 必须展示 `resources` 全量**，尤其是 shell 复合命令与 patch 的多文件。只显示 action 会掩盖风险。
- **`always` 的影响范围**：它会写入项目级持久规则。控制面应显示“将保存为：`shell: git status * → allow`”之类的提示，并提供后续管理入口（`/api/permission/saved`）。
- **`reject` 会连带拒绝同会话其他待处理请求**。UI 要提示这一点，避免用户误以为只拒绝当前项。
- **`permission.asked` 无 durable 字段**：它不保证可重放。控制面断线重连后应调用 `GET /api/permission/request` 补全待处理列表，而不是依赖事件重放。
- **不要把 policies 当作“审批规则”**。policies 不会出现在审批列表里，也无法被用户同意绕过；控制面若提供“管理员限制”，应生成 policies（最好通过托管配置）而不是私有开关。
- **托管优先级**：macOS managed preferences / 系统配置 / Console 覆盖用户与项目。控制面无法、也不应绕过。
- **V1 迁移**：`permission` → `permissions`，`bash` → `shell`，`task` → `subagent`，`write`/`patch` → `edit`。V2 默认允许外部目录访问，需要显式加 `external_directory` 规则恢复 V1 行为。
- **MCP / skill / plugin 的 deny 会直接移除对象**，UI 可能“看不到”而不是“看到但灰掉”；需要给出原因（policies）而不是空白。
