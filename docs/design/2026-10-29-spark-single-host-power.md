# Spark 单机服务管理与安全关机

日期：2026-10-29。状态：用户已确认设计；已实现第一阶段只读状态与预检，执行/维护/恢复阶段尚未实现，未进行真实关机。

## 目的和边界

用户希望在 Lework 内管理当前连接的 Spark，出差携带前有明确的关闭流程。第一版只管理当前后端绑定的一台物理主机；Wi-Fi、有线均可。管理员操作影响这台主机上的所有使用者。普通用户不能执行启停或关机。

提供“启动本机模型”“停止本机模型”“安全关机”三项能力，按部署实际能力开放。没有可管理的本机模型时，前两项不可用并显示原因。停止模型不代表主机已经关机。关机后开机仍通过设备自身方式完成，不做远程唤醒。

不控制另一台 Spark，不操作互联网卡，不把断网当成关机成功，不因超时强制杀任务，不改变既有手填地址和发现流程。若本机模型属于跨机部署，第一版不提供该模型的启停；本机关机会影响依赖它的跨机业务，不能承诺另一台业务不受影响。

## 现场事实（只读核对）

- 当前主机 `spark`，Wi-Fi 地址 `172.16.0.64`；K3s 只有节点 `master`。
- `lework-prod` 中运行 Lework、IAM、Worker、MySQL、PostgreSQL、Redis、NATS、Traefik。
- 后端镜像为 `v0.6.5_0a863bb0-enterprise-arm64`，Worker 为 `v0.6.4-1_397b23c9-arm64`。本地开发继续基于 v0.7.1，不能假设远端支持新接口。
- `leros-model` 没有 Pod selector，Endpoint 是本机 CNI 网关 `10.42.0.1:58089`，对应 Docker 中的 PerfxCloud nginx；nginx 转发至 `perfxcloud-app:3000`。
- 在可见的 Kubernetes 工作负载、Docker 容器、systemd 服务及 GPU 计算进程中，尚未发现运行中的独立本机推理服务；后续只读全量清单发现 10 个已退出的模型相关容器，尚未登记为可控目标。这不足以证明模型在另一台机器，也不足以证明入口停止等于模型停止。
- PerfxCloud 同时有自己的 MySQL、Redis、MinIO 和 autoheal。整机关机必须覆盖这些本地有状态服务，不能只关闭 Lework Worker。
- K3s 服务为 `KillMode=process`，不能以 `systemctl stop k3s` 的返回值证明其所有容器已退出。
- 本地源码已有 Worker 状态查询及 `StopAdmission` / `Drain`；后者当前用于进程退出且不可恢复。现有 `ShutdownWorker` 只是发送 WebSocket 消息，不能作为主机关机接口。

## 方案选择

1. 客户端通过 SSH 执行命令：验证快，但每个用户需要设备系统账号和权限，不符合普通管理员直接使用 Lework 的目标。
2. 后端容器直接拥有宿主机控制权限：实现路径短，但将整机权限混入业务容器，服务停止后也难以继续跟踪关机。
3. **建议采用：现有后端鉴权 + 本机管理服务。** 运维安装时绑定主机与固定服务清单，客户端只发起类型明确的操作。本机管理服务在业务服务退出后继续执行关机。

## 权限与主机绑定

- 后端验证真实登录态、部署所绑定的组织和管理员权限；使用现有账户适配层，在服务端重新校验。仅有前端 `is_admin` 或现有 Worker 状态接口的组织校验不够。
- 安装时登记稳定主机 ID、允许的组织 ID、本机 Worker 和模型目标、管理协议版本。发现记录只用于连接，不是授权凭证。
- 初版管理服务通过宿主机 Unix socket 接受后端调用。socket 只挂载给指定后端，使用单独组权限；不开放无认证局域网控制端口，不挂载 Docker socket 给前端或普通业务 Worker。
- 管理服务接收固定操作枚举与目标 ID，目标只能来自 root 管理的白名单。不接受 shell 命令、任意路径、任意 IP 或任意 unit 名称。底层按参数数组执行固定程序。
- 后端提供已鉴权的能力、状态、预检、创建操作、查询操作接口；客户端不直接调用宿主机控制接口。旧后端返回不支持时禁用操作，不能退化为 SSH 或猜测命令。
- 关机前确认框显示主机名、地址、影响范围和任务状态，用户点击确认才创建操作。普通查询、刷新或登录不得触发执行。

## 状态与操作契约

状态分别表达主机、模型、Worker 和当前操作，避免用一个在线灯代表全部。

模型状态：未配置 / 不支持管理 / 已停止 / 启动中 / 就绪 / 停止中 / 异常 / 状态未知。就绪需要进程或容器状态与模型健康检查同时通过；HTTP 入口可访问不能单独代表模型已加载。

操作包括唯一 ID、请求幂等键、主机 ID、当前启动标识、动作、阶段、开始时间、最近更新时间、错误码及可读原因。每台主机一次只执行一个变更操作；重复请求返回原操作。查询超时或客户端断网只显示状态未知，不重发新的关机操作。

阶段：预检 → 阻止新任务 → 等待已有任务 → 停止目标服务 → 发起系统关机（仅关机操作）。失败停在实际阶段，列出已停服务和未完成步骤，不伪造恢复成功。

管理服务将关键阶段和原有服务期望状态写入本机持久文件（原子替换并刷盘）。重启后将旧操作标为中断/待核对，不自动重放关机。执行前复核主机启动标识，拒绝旧预检票据。

## 启停和关机流程

### 模型启停

仅操作明确登记为本机、非分布式的推理服务，管理适配器负责其期望状态、实际进程和健康检查。当前 PerfxCloud 入口不登记为推理服务，初始模型启停显示“未配置可管理的本机模型”。后续查明真实本机服务后再接入适配器，不冒充已完成模型集成。

停止前先阻止新增模型请求并等待已有请求结束，同时阻止依赖该模型的本机 Worker 接收新任务。需要覆盖实际模型的所有调用入口；若还有绕过受控入口的调用方且适配器不能验证其请求结束，则停止能力不可用。模型重新就绪后才恢复对应准入。

### 安全关机

1. 预检确认所有受影响本地工作负载、后台写入服务、控制器及恢复策略已经登记。检查范围为本机 Kubernetes 非系统工作负载、Docker 业务容器和登记的独立模型/业务 systemd 服务；该范围内存在未登记目标、远端 Worker/模型依赖无法确认、状态过期或控制能力缺失时拒绝执行。Kubernetes 系统组件和普通系统服务由操作系统正常关机处理，不承诺检测任意宿主机进程或桌面程序的未保存内容。确认框提醒保存本机正在编辑的内容；预检尊重系统关机阻止器，执行时不绕过阻止器、不强制关机。
2. 设置持久维护状态，从服务端和 Worker 消费端同时停止新任务进入；排队、恢复、重试及定时投递必须遵守同一维护状态。等待已经接收的任务与模型请求结束。交互等待的任务仍算运行中，不能按 GPU 空闲判断完成。
3. 第一版默认等待最多 5 分钟。超时不强杀、不关机，保留维护状态并显示阻塞任务。管理员可以在处理任务后重试；恢复接单须明确操作并重新确认依赖健康。
4. 暂停会自动拉起工作负载的控制器，再按依赖停止本机 Worker、已登记模型和业务写入服务；最后停止对应数据服务。停止模型不能通过删除 Pod 完成后任由 Deployment 重新拉起。PerfxCloud autoheal 也必须纳入停机顺序。
5. 停机计划须在第一项变更前持久化，包含完整依赖顺序、原有期望状态、重启恢复方法。管理服务脱离业务数据库和 NATS 独立执行后半段。任何目标未正常退出或触发强制终止时，终止自动关机，报告失败；这不能保证其他已经停掉的服务自动恢复。
6. 本机管理服务调用系统正常关机接口，不采用强制断电、强制 kill 或集群级 drain。OS 接受请求后记录“系统关机请求已接受”；客户端可在失去连接前获得的最后状态不一定达到此阶段。
7. 客户端失联后显示最后已确认阶段和“最终关机状态待确认”。**不显示“已关机”或“可以拔电”**。纯网络软件没有关机完成后的独立供电证据。未来若接入可信硬件状态再增加已关机确认。

恢复接单必须可逆。现有 `StopAdmission` 不能直接充当维护开关，需要新增可恢复、可持久化的维护协议，同时保留退出使用的不可逆关闭路径。任务快照必须与维护确认关联，防止先读到零任务后又接单的竞态。

### 失败和开机恢复（本次建议的默认行为）

后端/IAM 退出前，管理员可通过客户端查询和恢复；退出后，客户端只能显示最后确认阶段，不能承诺继续查询具体失败原因。第一版不增加独立局域网恢复端口。运维通过 SSH 或设备本地终端调用受限管理程序的固定 `status` / `restore` 子命令，读取本机操作记录并按依赖顺序恢复原有期望状态。该维护命令需要宿主机管理员权限，不要求普通 Lework 用户持有 SSH 账号。

人工开机后，本机管理服务根据持久计划恢复原本运行的服务和必要控制器，让后端/IAM 及管理页面重新可用；原本已停止的模型保持停止。维护标记先于业务服务启动生效，开机不自动接单；依赖健康后由 Lework 管理员明确恢复接单。恢复失败保留记录与维护标记，由上述固定运维命令处理。安装包必须包含该恢复程序、启动排序和运维说明；未验证恢复前不得开启真实关机能力。

## 开发与现场启用

这是跨桌面、后端、Worker 和宿主机部署的功能，按以下顺序交付，避免用界面掩盖缺失的设备能力：

1. 在 v0.7.1 工作区建立类型化协议、管理员鉴权、能力检测和状态/预检界面；管理服务先使用模拟执行器。验收无权限、旧后端、未知模型、任务忙等行为。
2. 实现本地受限管理服务、维护协议及固定部署适配器。现场预检只读输出目标及顺序。未证明 Kubernetes 控制器可暂停、恢复和容器正常退出前，真实关机能力保持关闭。
3. 整理升级及回退清单，覆盖现有后端、IAM 兼容、Worker、数据库迁移和管理服务。功能开发不自动升级当前 v0.6.5 后端。现场启用需另选维护窗口。
4. 在用户选择的时间真实测试：先有任务时拒绝/等待，再正常停服务，再发起关机，最后人工开机验证服务恢复和数据完整。用户之前暂不重启的选择继续有效，当前只读调研不触发关机。

Kubernetes/Docker 适配器的具体命令及依赖图由实施阶段通过测试部署确定；不能先把当前主机用作破坏性探索环境。若适配器尚不支持现场部署，就如实显示不支持安全关机，不用普通 OS 关机代替通过全部检查的流程。

## 验收

- 非管理员、其他组织、过期会话无法创建操作；前端改参数不能扩大目标范围。
- 主机绑定错误、未知模型、旧后端、快照过期均不能执行；其他 Spark 不接收任何控制请求。
- 幂等、并发点击、维护期间新任务、重试与重启恢复均有行为测试。
- 任务超时、服务停止失败、控制器重建、数据服务拒绝退出均禁止进入系统关机步骤。
- 模型启动以健康检查确认；模型停止以进程退出和期望状态确认，不能只看端口不可达。
- 网络断开与系统接受关机严格区分；没有独立证据不得出现可拔电承诺。
- 真实关机、人工开机恢复、存储检查分别记录验收结果；模拟测试不替代实机结果。

## 第二阶段实现记录：持久维护准入

已增加只读状态文件协议与宿主机写入原语，接入真实 Worker 接单/恢复、Server 新任务入口和后台可靠任务投递。未配置的部署不改变行为；已配置但状态不可读时拒绝新任务。暂停前接收的任务继续执行，重启后积压任务等待显式恢复。准入和恢复登记与状态快照使用同一屏障；遗留 processing 记录只在订阅前重置，延迟恢复不会覆盖恢复接单后的运行任务。延迟恢复失败在状态中标记 degraded。

Server/Worker 通过整目录只读挂载读取同一份持久状态。写入使用修订号、操作 ID、文件锁和原子替换；禁止通过删除状态文件绕过维护。维护观测包含主机绑定，前端区分尚未接入、未知、暂停和接单。具体配置及权限约束见部署 README。

本阶段没有开放维护变更 API，也没有部署到现场。完整排空控制器、服务/模型停止与恢复、开机恢复及 OS 关机仍待实现与验收。代码测试通过不能替代实机停机/开机验收；当前仍不能通过客户端关闭设备。

第二阶段校验：Worker/状态读取 race 测试、维护相关 Go 测试、Python 23 项、桌面 55 项、状态层 84 项通过；Go vet、默认及 enterprise 构建、桌面两套类型检查和私有化构建通过。全量 Go 测试仍仅出现既有 `TestComputeOccurrenceWindow_IntervalAnchorGrid` 失败。独立审查无 Critical/Important；两项低风险待补：中间件放行测试应使用真实取消/审批路由，前端维护状态应严格验证字符串类型（当前异常数组会回退为“尚未接入”，不会启用操作）。
