## 2. 鉴权（Task 4 完全没有覆盖，最重要的发现）

`opencode serve` 在 v2.0.32 中强制 HTTP Basic Auth，**所有 `/api/*` 和
`/api/event` 都要求认证**；没有认证时返回：

```http
HTTP/1.1 401 Unauthorized
www-authenticate: Basic realm="Secure Area"
{"_tag":"UnauthorizedError","message":"Authentication required"}
```

用户名固定为 `opencode`（服务端源码把 username 写死），密码按以下规则产生：

| 启动方式 | 密码来源 | 是否打印 |
|---|---|---|
| `opencode serve`（默认） | `OPENCODE_PASSWORD` → `OPENCODE_SERVER_PASSWORD` → 随机 32 字节 base64url | 若为随机密码，stdout 打印 `server password <...>` |
| `opencode serve --service` | `$XDG_CONFIG_HOME/opencode/service.json` 的 `password` → 随机 | **不打印** |
| `opencode serve --stdio` | 强制随机（会先删除两个 password 环境变量） | stdout 只打印 `{"url": ...}` |

关键结论：

1. **`--service` 忽略 `OPENCODE_SERVER_PASSWORD`。** 实测设置
   `OPENCODE_SERVER_PASSWORD=...` 启动 `--service`，用该密码请求仍然 401；
   实际使用的是 `service.json` 里的随机密码。
2. `--service` 会把注册信息写到
   `$XDG_STATE_HOME/opencode/service.json`（`id/version/url/pid/password`，
   权限 0600），密码文件是 `$XDG_CONFIG_HOME/opencode/service.json`
   （权限 0600）。
3. 默认 `serve` + `OPENCODE_SERVER_PASSWORD` 是可控、可隔离的启动方式。
   **生产 I0 已采用这一方式**：supervisor 固定 spawn 普通 `serve`，daemon 读取
   `OPENCODE_PASSWORD` → `OPENCODE_SERVER_PASSWORD`，都没有时生成 32 字节
   base64url 密码，同时注入子进程环境并交给 `opencode.Client`
   （`WithPassword`）。密码只存在于子进程环境和进程内，不出现在日志/错误里，
   也不回写到 `agent.yaml`。集成测试现在直接使用生产 spec，没有测试专用改写。

客户端 `opencode.New` 现在接受 `opencode.WithPassword(...)`，对普通请求和
SSE 都发送 Basic Auth；401 映射为 `ErrUnauthorized`，方便 supervisor 区分
「密码错」和「服务还没起来」。

## 3. 端点与 payload 的真实形状

### 3.1 健康检查（Task 4 的 `/api/health` 是错的）

```bash
curl -u "opencode:<password>" http://127.0.0.1:<port>/api/info
# 200 {"version":"2.0.32","pid":...,"urls":[...],"paths":{"tmp":"/tmp"},"capabilities":{"persistentPty":true}}
```

- 正确路径是 **`GET /api/info`**；`/api/health` 是 404。
- 语义（OpenAPI + 服务端实现）：200 就绪；503 启动/停止中（带
  `retry-after: 1`）；500 失败；401 密码错。
- 客户端 `Health` 已改为 `/api/info`；401 返回 `ErrUnauthorized`，503/500
  返回普通 `statusError`。

### 3.2 创建会话

```http
POST /api/session
Content-Type: application/json

{"location":{"directory":"/abs/path"}}
```

真实响应（外层是 `data` 包装）：

```json
{"data":{"id":"ses_...","projectID":"...","cost":0,
 "tokens":{"input":0,"output":0,"reasoning":0,"cache":{"read":0,"write":0}},
 "time":{"created":1793529419920,"updated":1793529419920},
 "location":{"directory":"/abs/path"}}}
```

- 目录必须放在 `location.directory`；**顶层 `directory` 会被静默忽略**，
  会话会落到服务端默认目录（实测是启动 cwd）。Task 4 的 body 恰好是对的，
  但响应解析是错的（`directory` 嵌套、时间戳是毫秒数字，不是 RFC3339）。
- `title` 可选；不传时响应里没有该字段。

### 3.3 列表

```http
GET /api/session?limit=50&order=desc
```

```json
{"data":[{"id":"ses_...","location":{"directory":"/abs"},"time":{...}}],
 "cursor":{"previous":"...","next":"..."}}
```

裸数组假设不成立，必须解外层 `data`。默认最新在前，默认页大小 50。

### 3.4 prompt（异步准入，没有 receipt 字段）

```http
POST /api/session/{sid}/prompt
Content-Type: application/json

{"text":"Reply with the single word OK"}
```

```json
{"data":{"id":"msg_...","sessionID":"ses_...",
 "time":{"created":1793529424240},"type":"user",
 "payload":{"text":"Reply with the single word OK"},"delivery":"steer"}}
```

- 返回的是**被准入的 inbox/user 消息对象**，`data.id` 同时是 inboxID 与
  user message ID；Task 4 猜测的 `{"receipt":"..."}` 不存在。
- 客户端 `Prompt` 现在返回 `data.id`；缺失时返回错误（幂等缓存不能缓存空值）。
- 请求体还支持 `files`、`agents`、`skills`、`metadata`、`delivery`、`resume`，
  I0 不使用。

### 3.5 消息

```http
GET /api/session/{sid}/message?order=asc&limit=200
```

```json
{"data":[
  {"id":"msg_1","time":{"created":...},"type":"user","text":"Reply with the single word OK"},
  {"id":"msg_2","time":{"created":...,"streamed":...,"completed":...},
   "type":"assistant","agent":"build","model":{"id":"deepseek-flash","providerID":"yygullm"},
   "content":[{"type":"text","text":"OK"}],"finish":"stop",
   "cost":0,"tokens":{"input":4697,"output":2,"reasoning":0,"cache":{"read":2560,"write":0}}},
  {"id":"msg_3","time":{"created":...},"type":"idle","outcome":"succeeded"}
],"cursor":{"previous":"...","next":"..."}}
```

- 消息是 union，用 `type` 区分：`user`（`text`）、`assistant`
  （`content[]`，文本在 `type:"text"` 的 part 里）、`idle`
  （`outcome` + 可选 `error`），另有 `system`/`synthetic`/`skill`/`shell`/
  `compaction` 等。
- **不是** `role` + `parts`；Task 4 的两个字段名都不对。客户端现在把
  `type→Role`、`text→Text`、`content→Parts`，并把 assistant 的 text part
  拼进 `Text`，同时保留 `Finish`/`Outcome`/`Error`。
- 默认最新在前；客户端显式传 `order=asc&limit=200`，保证一轮对话按时间顺序
  返回且尽量一页取完。
- 失败时 assistant/idle 带结构化错误：
  `{"type":"provider.quota","message":"...","status":429,"response":{"body":"..."}}`。

### 3.6 wait（实验段，路径必须带 `/api/experimental`）

```http
POST /api/experimental/session/{sid}/wait
# 204 No Content（会话 idle 后返回）
```

- `/api/session/{sid}/wait` 是 **404**；正确路径在 experimental 段。
- 客户端 `Wait(ctx, sessionID)` 用无总超时的 stream client，由 ctx 兜底；
  404/405 返回 `ErrExperimentalUnavailable`，集成测试据此回退到事件。
- 实测：prompt 后立即调用会阻塞到本轮结束；会话已 idle 时立即返回 204。
- 注意：404 也可能是「session 不存在」，当前实现统一视为 experimental
  不可用；调用方应在回退路径上继续用 messages 判定终态。

### 3.7 权限

```http
GET  /api/session/{sid}/permission          # {"data":[Permission.Request...]}
POST /api/session/{sid}/permission/{rid}/reply
Content-Type: application/json
{"decision":"once"}                          # 或 {"decision":"always","message":"..."}
# 204 No Content
```

`Permission.Request`（形状来自 OpenAPI 的 `Permission.Request`；本次没有真实触发，
事件 `permission.asked` 按 v2 事件定义携带同一个对象，待权限收紧后复核）：

```json
{"id":"per_...","sessionID":"ses_...","action":"shell","resources":["..."],
 "save":[],"metadata":{},"source":{"type":"tool","messageID":"msg_...","id":"..."},
 "message":null}
```

事件 `permission.asked` 的 `data` 就是该对象。用不存在的 requestID 实测返回：

```json
HTTP/1.1 404
{"_tag":"PermissionNotFoundError","requestID":"per_doesnotexist",
 "message":"Permission request not found: per_doesnotexist"}
```

- 三态 `once|always|reject` 未变；`always` 按设计应降级为 `once`（共享库会
  持久化规则，I0 没有撤销入口）。
- 本次真实 prompt 使用用户全局配置
  `permissions:[{"action":"*","resource":"*","effect":"allow"}]`，**没有触发
  权限请求**（watcher `replies=0`）。权限路径的真实「触发」仍需在收紧配置后
  补一次，见阻塞项 4。

## 4. 事件流、replay 与 seq

`GET /api/event` 是 SSE，必须带 Basic Auth：

```text
data: {"id":"evt_...","type":"server.connected","data":{}}

: heartbeat

data: {"id":"evt_...","created":1793529424244,"type":"session.execution.started",
      "data":{"sessionID":"ses_..."},
      "durable":{"aggregateID":"ses_...","seq":2,"version":1}}
```

- 事件没有 `event:` 名称行，也没有 SSE `id:` 行；`type` 在 JSON 里。
- `sessionID` 在 **`data.sessionID`**，不在顶层；Task 4 的顶层字段永远为空。
  客户端现在在解码时把它提到 `Event.SessionID`。
- `durable:{aggregateID,seq,version}` 只出现在可持久化的会话事件上；
  `seq` 是按会话（aggregate）单调递增的。非 durable 事件（`server.connected`、
  `provider.updated` 等）没有该字段。
- **`/api/event` 不支持 replay**：实测带 `Last-Event-ID: <evt_id>` 重连，只收到
  新的 `server.connected`，没有任何历史帧；`?cursor=7` 也被忽略。OpenAPI 里
  `GET /api/event` 没有任何参数。
- 另有一个按会话的事件日志：
  `GET /api/experimental/session/{sid}/log?after=<seq>&follow=false`。
  实测只返回一条 `{"type":"log.synced","aggregateID":"ses_...","seq":7}`，
  `after=0/1/7` 都没有历史帧。说明默认没有开启事件持久化；`after` 必须 ≥ 0
  （`-1` 返回 400）。
- 因此断流后的正确恢复方式是**快照重同步**：
  `GET /api/session/{sid}`（`outcome`、`time.idle`）+ `GET
  /api/session/{sid}/message`，而不是依赖 seq 重放。这与 Task 7 的
  `agent.resync_required` 设计一致；`durable.seq` 目前没有传给控制面
  （runner 仍写 `Seq: 0`），未来可作为 gap 检测的输入。

## 5. 共享服务与 attach

### 5.1 健康探测 attach（supervisor 已实现）

集成测试结果：

- 第一次 `Ensure`：spawn 1 次，`Mode=managed`。
- 第二次 `Ensure`：**spawn 次数仍为 1**，`Mode=managed`（Task 5 的约定：
  自己启动的进程不降级为 attached）。
- 新建一个「外来」supervisor 对同一端口 `Ensure`：`Mode=attached`，
  其 spawner 调用 0 次。

即：只要端口上的 `/api/info` 能通过（含认证），就能 attach，不会重复起进程。
生产 I0 的 supervisor 现在就是普通 `serve` + 共享密码，因此该 attach 语义在
生产路径上已生效；集成测试不再改写 spec。

### 5.2 `opencode serve --service` 的注册语义（重要限制）

在隔离的 XDG 目录下实测：

| 场景 | 结果 |
|---|---|
| 实例 A 在 47132 | 正常监听，注册写到 `$XDG_STATE_HOME/opencode/service.json` |
| 同 XDG 起实例 B（端口 47133） | B 覆盖注册；**A 立即退出**（日志只有启动行） |
| 同 XDG 再起实例 C（与 B 同 URL/端口） | C 立即退出，B 继续提供服务（attach 到 incumbent） |

结论：`--service` 是**每个 XDG 配置目录一个服务**，不是「每个端口一个」。
用不同端口起第二个实例会把第一个踢掉。多项目/多租户需要：
- 每个 agent 使用独立的 `XDG_CONFIG_HOME`/`XDG_STATE_HOME`/`XDG_DATA_HOME`
  （并预置 `service.json` 密码），或
- 直接用默认 `serve` + `OPENCODE_SERVER_PASSWORD`（I0 生产采用的方式）。

**I0 决策**：生产 supervisor 已改为普通 `serve`，**不再使用 `--service`**，
因此不会触碰 per-user 注册，也不会踢掉用户的托管服务。代价是 agent 自己的
服务与用户 TUI 默认连接的服务不是同一个，当前 TUI 看不到 agent 会话。
`--service` 的服务发现、XDG 隔离与 TUI attach 留到 I1 设计；本节的
`--service` 行为仍然有效，供 I1 参考。

**对用户 TUI 的影响（推断，未直接观察 UI）**：托管模式（`--service`）按 XDG
目录共享同一份注册和密码。如果 agent 用 `--service` + 不同端口启动，会替换注册并
导致原有托管服务退出；如果复用同一 URL/端口，则 TUI 与 agent 共用同一个服务/
数据库，TUI 理论上看得到 agent 创建的会话（本次只验证了服务端会话对同一服务可见）。

### 5.3 一个服务并发处理两个项目

在同一个默认 `serve`（47127）上，对 `/tmp/.../projA` 与 `projB` 各建一个会话，
并发 prompt `Reply with the single word OK`：

- 两个 prompt 都被准入；
- 两个 `wait` 分别 0.71s / 1.07s 返回 204；
- 两个会话的 assistant 都是 `OK`，`idle.outcome=succeeded`。

即共享服务可以并发服务多个 location/项目；I0 不需要 per-project 进程池来
满足功能正确性。是否要为隔离性做池化是 I1 的资源决策，不是 API 限制。

## 6. PTY API（仅探针，不实现）

```http
GET  /api/pty[?location[directory]=<abs>]
POST /api/pty
{"command":"/bin/sh","args":["-c","echo hi"],"cwd":"/abs","title":"probe","env":{}}
```

真实响应：

```json
{"location":{"directory":"<server default>"},
 "data":{"id":"pty_...","title":"probe","command":"/bin/sh",
         "args":["-c","echo hi","-l"],"cwd":"/abs",
         "status":"running","pid":1158537}}
```

- 创建时会自动给 args 追加 `-l`（登录 shell）。
- `location` 取自请求的 location 上下文（header/默认目录），不是 body 的
  `cwd`；用 `?location[directory]=projA` 过滤时，按 body `cwd` 创建出来的 PTY
  在 projA 下**查不到**（实测 `data:[]`）。需要 location 隔离时应通过
  `x-opencode-directory` 头或对应 location 的创建入口，而不是只传 `cwd`。
- 连接令牌：

```http
POST /api/pty/{ptyID}/connect-token
x-opencode-ticket: 1
Origin: http://127.0.0.1:<port>

{"location":{...},"data":{"ticket":"<uuid>","expires_in":60}}
```

  不带 `x-opencode-ticket: 1` 或 Origin/Host 不匹配 → 403
  `Invalid PTY connect token request`。随后用
  `GET /api/pty/{ptyID}/connect?ticket=<ticket>[&cursor=N]` 升级 WebSocket。
- `DELETE /api/pty/{ptyID}` → 204。
- `capabilities.persistentPty: true`（Linux）。另有
  `/api/experimental/persistent-pty/*`（create/read/update/remove/snapshot/
  handoff/connect-token），本次未展开。

## 7. 平台说明

- **Linux**：本次全部实测。子进程用 `Setpgid` + 进程组 SIGKILL 清理；
  `persistentPty` 可用；文件权限 0600。
- **macOS**：未实测。需要注意 `mktemp -d` 返回 `/var/...`，服务端可能回报
  `/private/var/...`（集成测试用 `EvalSymlinks` 比较目录）。密码/注册文件路径
  遵循 `$XDG_CONFIG_HOME`/`$XDG_STATE_HOME`，未设置时回落到
  `~/Library/Application Support/opencode`。`--service` 的注册冲突行为预计相同，
  但未验证。
- **Windows**：未实测。`supervisor/process_windows.go` 目前直接返回
  `ErrUnsupported`（Task 5 已记录），即 Windows 还不能监管 opencode 子进程；
  PTY 依赖 ConPTY，`x-opencode-ticket`/Origin 检查在浏览器外的客户端需要额外
  处理。`os.UserConfigDir` 是 `%APPDATA%`，密码文件 ACL 语义与 Unix 不同。
  结论：Windows 上 I0 只能做客户端侧探测，进程监管要等 I1。

   per-user 注册，因此没有该风险；I1 若恢复 `--service`/TUI 共享，必须为每个
   agent 隔离 `XDG_CONFIG_HOME`/`XDG_STATE_HOME`/`XDG_DATA_HOME`，见 5.2。
3. **没有事件 replay。** `/api/event` 忽略 `Last-Event-ID`，session log 默认
   只有 `log.synced`。断流只能靠 messages/session 快照重同步；如果要真正的
   gap 恢复，需要先确认 `events.persist` 配置是否开启（本次未改配置）。
4. **权限「触发」路径未真实跑通。** 当前用户配置全 allow，真实 prompt 没有
   产生 `permission.asked`；`permission.reply` 的路径/body/204 由 OpenAPI 和
   404 探针确认，自动回复逻辑已写进集成测试但 `replies=0`。收紧
   `permissions` 后需要补一次真实 `once` 用例。
5. **真实 prompt 依赖外部模型凭据。** 测试不注入 API key，依赖用户全局
   `~/.config/opencode/opencode.jsonc` 的 `yygullm/deepseek-flash`。若把
   `XDG_CONFIG_HOME` 完全隔离，opencode 会回落到内置 `opencode/big-pickle`，
   实测返回 429：
   `Free usage limit reached. Free models work in OpenCode ...`。
   这不是代码 bug，是外部前置条件；CI 里若要跑这个测试，需要注入 provider
   配置（密钥不能进仓库）。
6. **fresh XDG 目录下的首次 prompt 卡顿未完全定位。** 在一次隔离
   `XDG_*` + `OPENCODE_CONFIG=<用户配置>` 的探针中，`POST prompt` 和
   `GET /api/model/default` 超过 15s 无响应（服务端日志 499），
   怀疑是 `superpowers` 插件/模型元数据首次安装或刷新；默认 HOME 下未复现。
   本次测试不使用隔离 XDG，故不受影响；做生产隔离时需要预热或禁用插件
   自动安装后再确认。
7. **`Wait` 的 404 语义**：当前把 404/405 一律视为
   `ErrExperimentalUnavailable`，无法区分「接口被移除」与「session 不存在」。
   回退到事件时仍应以 messages/session 的终态为准。
8. **平台覆盖**：macOS/Windows 未实测；Windows 进程监管仍是
   `ErrUnsupported`。
