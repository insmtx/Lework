# 主张与证据控制

## 一、主张类型

写每个确定性句子前先判断其类型。

| 类型 | 含义 | 允许来源 | 推荐表达 |
|---|---|---|---|
| 招标要求 | 采购人规定的目标、条件或标准 | 正式招标来源 | “根据采购文件要求……” |
| 已确认事实 | 投标主体、项目、人员、产品的已核验事实 | `bidder-facts.json` | 直接陈述，并保持来源边界 |
| 已确认产品能力 | 材料明确证明的现有能力 | 产品说明、检测、截图、接口文档等 | “所投产品支持……” |
| 项目方案设计 | 为本项目提出、尚待实施的设计 | 要求、已有能力和合理工程设计 | “本项目拟采用……” |
| 实施动作 | 中标后由项目团队执行的工作 | 招标义务和已确认资源边界 | “实施阶段将……” |
| 投标承诺 | 投标方愿承担的明确义务 | 招标要求或用户明确确认 | “我方承诺……” |
| 验收目标 | 交付后需要验证的指标和判定 | 招标要求、合同或确认方案 | “验收时以……作为判定依据” |
| 待确认事项 | 事实、能力、参数或材料尚未确认 | `pending.json` | 使用明确占位或条件说明 |
| 背景知识 | 用于解释技术原理的稳定知识 | 可靠参考资料 | 仅解释原理，不写成项目事实 |

## 二、禁止的主张转换

- 招标规定“应达到”不能改写成“产品已达到”；
- 行业常见能力不能改写成“所投产品支持”；
- 计划开展测试不能改写成“已通过测试”；
- 材料缺失不能自动判定“无偏差”；
- 参考标书使用的参数不能移植到当前项目；
- “可以设计”不能改写成“系统现已具备”；
- “用户可能需要”不能改写成采购人既有现状。

## 三、证据状态

| 状态 | 写作处理 |
|---|---|
| 已有且适用 | 可以写确定性事实，并在适合位置引用材料或说明验证依据 |
| 已有但适用范围有限 | 只在材料覆盖范围内陈述，不扩大到其他版本、环境或场景 |
| 仅有招标目标 | 写成响应目标、设计约束和验收依据 |
| 可通过实施实现 | 写成项目设计和实施动作，不写成既有产品能力 |
| 待用户确认 | 使用待补或条件化表达；重要结论不得提前肯定 |
| 冲突或无效 | 不写入积极结论，回到事实/材料处理 |

## 四、数字、时限和绝对化词

金额、日期、版本、人数、并发、准确率、响应时间、到场时间、修复时间、质保期、授权期、节点数和兼容清单均属于高风险主张。没有正式要求、确认事实或有效材料时不得写具体值。

“永久、全部、任意、零故障、百分之百、唯一、领先、无缝、完全自动”等绝对化词需要明确依据和适用边界，否则删除或改为可验证的具体表述。
