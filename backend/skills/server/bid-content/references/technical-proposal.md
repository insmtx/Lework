# 技术方案写作

## 一、技术方案的目标

技术方案要证明：我方理解当前项目的业务对象和技术约束，提供的系统或服务能够通过清楚的架构、机制、流程、控制和验证方式落地，而不是仅有产品功能名称。

## 二、总体展开逻辑

技术方案可按项目需要选择：

- 项目理解与建设目标；
- 总体架构和系统边界；
- 端到端业务流程；
- 分项系统、模块或场景方案；
- 数据、接口和集成；
- 部署、适配与扩展；
- 性能、高可用与运维；
- 安全、权限、日志和审计；
- 测试验证、风险和交付。

这些是主题库，不是固定目录。必须服从锁定目录和招标要求。

## 三、技术内容单元

每个技术主题至少说明：

1. **对象与约束**：处理什么、面向谁、受什么招标或环境条件约束；
2. **设计结论**：本项目准备采用什么总体做法；
3. **输入与前提**：输入数据、系统、环境和依赖是什么；
4. **关键机制**：采用什么机制解决问题，为什么适合当前项目；
5. **处理流程**：步骤、顺序、状态和模块关系；
6. **质量与控制**：校验、权限、监控、日志、阈值或人工复核；
7. **异常与边界**：失败、超限、格式异常、依赖不可用时如何处理；
8. **输出与验证**：输出结果、接口、文档、记录、测试和验收方式。

## 四、总体架构

架构章节不能只有分层名称。需要解释：

- 每层解决的项目问题；
- 各层/模块的职责边界；
- 数据、请求、任务和结果如何流转；
- 与采购人既有系统的接口位置；
- 安全、运维和审计能力如何贯穿；
- 如何支持部署、扩展、故障隔离和后续场景。

架构图中的每个主要模块都应在正文中得到解释。

## 五、功能与场景

功能不能按菜单逐项复述。优先从业务场景和处理链展开：

```text
业务发起
→ 输入校验
→ 核心处理
→ 质量控制
→ 结果输出
→ 反馈或异常闭环
```

只有在需要精确对照招标功能项时使用功能对照表，表后仍需解释关键机制。

## 六、性能和指标

- 逐项保留招标指标的对象、单位、条件和判定口径；
- 没有现成测试材料时，只能说明设计措施、测试环境和验收方法；
- 并发、响应时间、吞吐、准确率、可用性等必须说明样本、负载、硬件、统计口径或适用前提；
- 不得把实验条件下的结果扩大到所有环境；
- 扩展能力要说明增加什么资源、如何接入、是否影响业务和如何验证。

## 七、接口和数据

接口方案至少覆盖：调用方、服务边界、请求数据、任务标识、同步/异步、查询、回调、鉴权、幂等、重试、超时、错误码、日志和联调。接口字段只能来自真实接口文档或写成项目设计，不得伪造现有接口。

## 八、部署和适配

明确目标环境、节点、网络、存储、依赖、授权、安装、配置、健康检查、备份、升级、回退和验证。兼容性范围必须有来源；没有确认的版本或平台不能列为已支持。

## 九、安全和运维

从保护对象和威胁边界出发说明身份、权限、数据、接口、日志、审计、监控、告警、漏洞和事件处理。不能用“多重保障”“绝对安全”代替控制措施。

## 十、技术深度检查

出现以下情况需返工：

- 只有功能名和宣传语；
- 有架构图但没有调用关系；
- 有流程但没有异常路径；
- 有指标但没有测试口径；
- 有安全章节但没有保护对象和审计记录；
- 有部署章节但没有前置条件和回退；
- 有接口章节但没有任务生命周期和错误处理；
- 有方案结论但无法对应交付物或验收证据。

## 十一、技术正文的表达节奏

技术章节不要从参数或菜单开始。每个主要主题先用一段说明项目定位和技术矛盾，再展开机制、流程和控制，最后收束到输出和验收。

推荐使用以下句子关系：

```text
基于【项目目标/现状】，我方将【主题】定位为【作用】。
针对【约束/难点】，为此采用【机制】，由【角色/模块】完成【动作】。
首先【准备/校验】，随后【处理/联调】，最终【输出/验证】。
```

句式只表达真实逻辑，不机械重复。已确认的产品事实、当前项目设计和投标承诺必须使用不同主语；连续的“支持……实现……确保……”应改写为对象明确的动作链。
