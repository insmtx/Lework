# 结构化投标正文写作

## 一、正文的核心任务

投标正文要帮助评审人完成判断，而不是展示术语数量。正文的基本单位不是一条功能或一行表格，而是一个能够说明“项目为什么需要、我方如何处理、如何证明完成”的论证主题。

每个实质主题需要覆盖以下内容中的主要部分：

1. 当前项目的目标、对象或约束；
2. 我方对问题的判断和方案定位；
3. 机制、步骤、角色和输入输出；
4. 质量控制、异常路径和责任边界；
5. 形成的结果、记录、交付物和验证方式。

简单字段可以直接填写；复杂或评分权重高的主题才展开完整论证。

## 二、句式风格

真实标书的正式感来自句内关系和责任主体，不来自形容词或生硬的长句。句子应尽量形成“判断—动作—条件—结果”的关系。

### 推荐的句式动作

```text
项目判断：基于对【目标/现状】的理解，我方将【主题】定位为【作用】。
问题转方案：针对【约束/难点】，为此采用【机制】，由【角色】完成【动作】。
流程递进：首先【准备/校验】，随后【处理/联调】，最终【交付/验证】。
结果收束：通过【记录/测试/复核】，形成【输出】，由【角色】确认【判定】。
```

这些是句式动作，不是每段都要照抄的模板。实际写作中可使用“同时、其中、因此、从而、在……条件下”等连接词，但每个连接词必须表达真实的逻辑关系。

### 主语和动词

- 已确认的产品能力使用“所投产品/平台已具备……”；
- 当前项目设计使用“本项目拟采用……”；
- 实施和服务承诺使用“我方/本公司将……”；
- 过程动作优先使用“接入、拆分、调度、校验、复核、隔离、回传、记录、归档、验收”等可执行动词；
- 同一责任链可以保持同一主体；只有责任边界变化时才切换主语，并避免连续使用同构的“支持……实现……确保……”。

## 三、段落推进

复杂主题默认采用以下段落动作：

```text
开篇定位段
→ 说明项目问题、价值和本节结论

机制展开段
→ 说明对象、输入、模块关系、处理步骤和责任角色

控制收束段
→ 说明异常、质量控制、输出记录、交付和验证
```

一个主题可以由三段组成，也可以把相邻动作合并为一段。相关句子应围绕同一结论合并成自然段，不按“一句一个事实”换行。重点不是字数，而是段落承担的功能不同。段落应有短有长：开篇和收束可以简洁，重点难点、流程机理和实施策略应保留完整论证。高分主题必须绑定至少一个当前项目对象、边界或验收口径；没有依据时暂停或使用明确占位。

推荐的段落形态是：

> 先下一个项目判断，再解释为什么这样判断；随后说明我方如何组织机制和流程；最后落到控制点、交付物或验收方式。

避免“标题—一句总述—一张功能表”的固定重复结构。

复杂章节使用主题论证；原子要求、固定字段和低复杂度事项仍可使用“条款—响应—证据”矩阵，不为追求叙事感而扩写。

## 四、先关系后功能

复杂方案先建立总体关系：

- 用户、业务系统、平台和外部依赖的关系；
- 数据、请求、任务和结果的流向；
- 各模块职责、调用顺序和交接点；
- 正常流程、异常路径和恢复方式；
- 实施、测试、培训、运维和验收的衔接。

关系清楚后再展开功能、参数和界面。功能对照表只能压缩已解释的内容，不能替代总体方案。

## 五、正文、表格和图示分工

- 正文：解释原因、机制、流程、边界、例外和结论；
- 表格：适合参数对照、角色职责、阶段计划、风险、测试项和交付物；
- 图示：适合架构、业务流程、部署、数据流、任务流和模块关系；
- 产品截图：只证明真实界面或真实结果，不替代机制说明；
- 附件：证明资质、案例、授权、检测和承诺。

图表出现前说明其用途，出现后解释关键关系。没有真实图片时，用有明确列语义和顺序的流程、职责或接口表替代，不生成装饰图或伪造截图。

## 六、评审导航和交叉引用

章节开头可以用一段简短导航说明本节的判断路径，但不要写“以下将从几个方面展开”等空引导。应直接说明本节将回答的项目问题、方案主线和验证结果。

引用其他章节或附件时必须说明：

- 引用对象名称；
- 其证明的具体事项；
- 当前章节仍需保留的必要结论。

不能只写“详见相关章节”或“详见附件”。

## 七、句式示例

弱写法：

> 所投产品支持多格式文件识别，并提供批量处理接口。

合格写法：

> 针对【当前项目的文档来源和接入约束】，我方将把格式识别和批量处理作为统一处理链的入口控制。系统先完成文件类型识别、可读性校验和任务登记，再按文件类型进入后续处理；异常文件保留失败原因和重试记录，最终以【已确认的交付物或验收记录】作为交付和验收依据。

合格写法不是把一句话机械拉长，而是补足项目判断、动作链和可验证结果。方括号内容必须由当前权威输入重建，不能用参考标书事实或通用流程替换；无法重建时暂停该主题或保留占位。

## 八、项目针对性测试

编辑时执行以下测试：

- 删除项目名称后，正文是否仍能用于任意项目；
- 是否出现当前项目的真实业务对象、技术边界、部署条件或验收要求；
- 是否说明该能力如何进入当前项目完整处理链；
- 是否有与当前要求和材料对应的验证方式。

若大部分内容可原样复制到其他项目，判定为项目针对性不足。

## 九、禁止的低质量写法

- “我方完全响应，系统功能强大、性能先进”；
- 连续罗列“支持……支持……支持……”而不解释处理逻辑；
- 每个小要求都设置三级标题，造成目录碎片化；
- 用一张功能表代替技术方案，用一张进度表代替实施方案；
- 用“及时响应、快速处理”代替服务流程和承诺边界；
- 用“严格按照要求验收”代替测试环境、步骤和判定；
- 连续重复“通过……实现……确保……”或“本章……以下逐项说明……”；
- 用宣传口号和形容词填充篇幅；
- 机械复制招标原文并把“应”改为“可”。
