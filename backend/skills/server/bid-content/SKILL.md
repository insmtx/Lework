# 投标文件内容编写

把上游已经确认的要求、目录、模板填写目标、事实和材料，转换为 `work/填充内容/` 下可直接回填的 Markdown。优先直接成稿；只有复杂、评分权重高或跨章节的正文才使用临时写作卡。

## 一、职责边界

负责：

- 按锁定目录处理所有动态叶节点；
- 按底板和 `填写说明.md` 理解正文插入点、字段、表头、合并关系和签章区；
- 编写技术、实施、服务、培训、验收等正文；
- 填写固定表单、简单字段和普通数据表；
- 在正文完成后生成索引表和商务/技术偏差表；
- 把待补事项写入待补清单或正式占位。

不负责：

- 修改 `目录.json`、可填写底板或 `填写说明.md`；
- 在 DOCX 回填阶段重新设计、扩写或解释正文；
- 执行独立终审或发布审批；
- 编造企业、产品、案例、人员、证书、参数、价格、时限、服务等级或验收结果；
- 把 `REQ-*`、`FACT-*`、`MAT-*`、`PEND-*`、`OUT-*` 写入正式投标内容。

## 二、进入条件与权威输入

进入前读取并确认以下输入存在且版本一致：

| 输入 | 权威路径 | 用途 |
|---|---|---|
| 锁定目录 | `work/投标文件/目录.json` | 章节顺序、层级、叶节点和正式标题 |
| 可填写底板 | `work/投标文件/模板/可填写底板.docx` | 固定文字、表格结构、签章和版式边界 |
| 填写说明 | `work/投标文件/填写说明.md` | 每个目标的位置、内容形态和保护规则 |
| 原子要求 | `work/招标/requirements.json` | 要求、来源、属性和评分点 |
| 覆盖关系 | `work/招标/coverage.json` | 要求与响应节点、附件和待补项的关系 |
| 事实基线 | `work/项目/bidder-facts.json` | 投标方、产品和项目的可用事实 |
| 材料索引 | `work/项目/material-index.json` | 材料能证明的事实及适用范围 |
| 待补清单 | `work/项目/pending.json` | 缺失、冲突和提交前需补齐的内容 |

关键输入缺失或冲突时，只暂停受影响节点并记录原因；不通过“完全响应”“严格执行”等套话掩盖问题。

## 三、内容分流与产物

先根据目录和填写说明分流，不额外生成全局任务清单：

| 节点类型 | 默认处理 | 正式产物 |
|---|---|---|
| 固定表单/简单字段 | 直接按模板填值 | `内容.md` |
| 普通数据表 | 读取表头后逐行填写 | `内容.md` 或业务语义文件 |
| 简单叙述章 | 直接按要求—方案—验证成稿 | 一个 Markdown 文件 |
| 复杂/高分叙述章 | 可先写一份简短章节写作卡 | 一个 Markdown 文件；写作卡留在临时区 |
| 索引/偏差表 | 所有正文完成后批量生成 | `内容.md` |
| 附件说明 | 按材料索引编排和占位 | `内容.md` |

正式区只保存可回填 Markdown 和正文实际引用的资源：

```text
work/填充内容/<目录叶节点>/
├── 内容.md
├── <按真实业务逻辑拆分的小节>.md
└── resources/                 # 仅存正文实际引用的资源
```

临时区只在确有帮助时使用：

```text
work/.tmp/bid-content/
├── 参考写作画像.md             # 有真实参考标书且确需复用时，项目级一次
└── <复杂叶节点>/章节写作卡.md    # 复杂/高分章节可选
```

不创建 `draft/`、`candidate/`、逐章完成检查或逐表字段分析文件。

## 四、按需读取参考

默认只读取：

- `references/content-contract.md`；
- `references/language-and-writing-discipline.md`。

按内容类型追加读取：

| 场景 | 读取参考 |
|---|---|
| 证据与主张边界 | `claim-evidence-control.md` |
| 技术方案 | `technical-proposal.md`、必要时 `chapter-patterns.md` |
| 实施与项目管理 | `implementation-plan.md` |
| 测试与验收 | `acceptance-plan.md` |
| 服务与售后 | `service-after-sales.md` |
| 培训与知识转移 | `training-plan.md` |
| 表格/偏差表 | `table-content-writing.md`、`deviation-table-writing.md` |
| 真实标书存在 | `reference-bid-learning.md`、`templates/参考写作画像.md`、必要时 `visual-evidence-planning.md` |

不要为了“完整”一次性读取全部参考，也不要把参考规则复制成新的过程文件。

## 五、写作风格契约

真实标书只迁移写法，不迁移事实。存在参考标书时，先在项目级临时区形成一次 `参考写作画像.md`，后续章节直接复用，不逐章重复研究。

### 1. 句子怎么写

- 先写判断，再写动作；句子应说明对象、关系、条件和结果，不把功能名当成正文；
- 优先使用真实的因果、目的、转折和递进关系，例如“针对……，为此……；同时……，最终……”；不要为了像标书而机械堆叠连接词；
- 技术和服务章节使用主动责任主语：`我方`、`本公司`、`本项目实施团队`，产品既有能力才使用`所投产品`；
- 用“配置、承接、调度、校验、复核、隔离、回传、记录、归档、验收”等动作词替代连续的“支持、提供、实现、确保”；
- 同一主题可以连续使用同一责任主体；只有责任边界发生变化时才切换主语，并避免连续使用同构的“通过……实现……”句式；简单字段和明确参数不为追求句式而扩写。

### 2. 段落怎么推进

复杂或高分主题默认按以下段落动作推进：

```text
开篇判断/项目定位
→ 项目问题与约束
→ 方案机制与处理流程
→ 控制、异常与责任边界
→ 输出、交付与验证
```

开篇段回答“本主题为什么对本项目重要”，中间段回答“我方具体怎么做”，收束段回答“形成什么、由谁确认”。同一结论的相关句子合并为自然段，不按“一句一个事实”换行；不把每一条要求拆成独立短段，也不把一张表当成完整方案。复杂主题至少绑定一个当前项目的真实对象、边界或验收口径；无法绑定时暂停受影响节点或保留明确占位，不用通用流程补空白。

### 3. 章节怎么成形

- 先建立项目理解、总体关系或业务主线，再展开模块、功能和参数；
- 高分/复杂章节采用主题段落；低复杂度或原子条款继续使用条款—响应—证据结构，不套用完整三段闭环；
- 三级标题只对应独立的评审、实施或验收主题；相关要求应合并为一个主题，通过段落、列表或表格展开；
- 重点主题使用“短段引入＋完整论证段＋控制/交付段”的混合节奏，不能所有段落长度和句式完全一致；
- 图表前说明要证明什么，图表后解释关键关系；没有真实图时，用有完整字段和时序的流程表、职责表或接口表替代。

## 六、快速执行流程

### 1. 读取并分流

按目录顺序读取当前节点对应的要求、填写说明、事实、材料和待补项，立即判断它属于固定表单、普通表格、简单正文、复杂正文、索引/偏差表或附件说明。

### 2. 直接处理固定表单和普通表格

- 保留固定文字、标点、顺序、下划线、括号和签章区；只填明确开放的字段；
- 先理解表头和“一行代表什么”，再逐格填值；
- 合并表头、响应位置、页码、偏差表和高风险字段必须以底板/填写说明为准；
- 普通表格不单独生成字段分析文件；遇到语义不清时在当前上下文中记录判断并停止该表，不猜测。

### 3. 直接编写叙述型正文

简单章节直接写正式 Markdown。复杂或高分章节才使用 `templates/章节写作卡.md`，且只写一份卡片，不再拆研究、骨架、初稿和候选稿。

正文按以下顺序组织：

```text
章节开篇判断
→ 要求/评分点与项目对象
→ 总体关系和设计结论
→ 实现机制与处理流程
→ 控制点、边界和异常
→ 交付物、记录和验证方式
```

复杂或高分主题至少形成一个定位段、一个机制/流程段和一个控制/验证段；简单事项可合并回答。每个三级论证单元要能回到“为什么、怎么做、如何控制、形成什么、如何验证”，但不要求每个段落机械重复同一顺序。三级标题只用于真实论证单元，不为凑层级制造空标题。

写作时优先直接保存最终 Markdown。只有需要大幅返工或多人交接时，才在临时区保留写作卡；不为流程本身创建多个版本文件。

### 4. 后置生成索引和偏差表

全部正文、资格材料说明和附件位置完成后，再一次性生成资格/评分索引及商务/技术偏差表：

```text
招标条款 → 真实响应章节 → 偏差结论 → 待补清单
```

`响应文件章节及条款号` 只填写真实目录节点和条款位置。每个商务或技术偏差表行只对应一个来源条款，且逐条写明具体偏差说明：无偏差时使用“完全响应，无偏差。承诺【与本条款直接对应的已确认履约内容】。”的结构；正、负或部分偏差必须逐条写明实际差异。材料缺口、工作备注和内部编号只进入待补清单。

### 5. 交接

交给 `bid-backfill` 的只有锁定目录、填写说明、正式 Markdown、真实资源和待补清单。回填阶段不得补写或改写正文。

## 七、事实、证据与响应结论

区分以下主张：招标要求、已确认事实、已确认产品能力、项目设计、实施动作、投标承诺、验收目标和待确认事项。

- 招标指标是响应目标，不自动等于产品既有能力；
- 设计方案写成“本项目拟采用”，不能写成“产品现已具备”；
- 未发生的测试、验收和性能结果不能写成已通过；
- 已决定承担且仅缺佐证材料时，可以写“完全满足/无偏差”，缺口记录到待补清单；
- 能力、资格或承诺本身尚未决定时，使用明确的 `【待确认：...】`，不能用“无偏差”掩盖；
- 参考标书只提供结构、论证顺序和图表节奏，不能提供当前项目事实。

## 八、表格与图证规则

- 表头决定字段语义，一个单元格只承担当前列的语义；
- `响应文件章节及条款号` 是位置，不是响应正文；
- `偏差说明` 是偏差结论，不是材料缺口；
- 页码在最终排版后回填，不猜测；
- 金额、日期、人员、证书、业绩、参数和服务时限只能来自权威输入或用户已确认承诺；
- 图、截图和测试证据必须真实、可追溯并在正文中解释用途；没有真实图片时用流程、职责或接口表替代，不留“此处放图”的空占位。

## 九、结束前的一次自检

不生成检查报告，写作者在交接前快速确认：

- 每个动态叶节点都有正式内容或明确阻塞原因；
- 正文覆盖相关强制项和评分点，且包含项目对象、机制、控制和验证；
- 主要主题有项目化开篇判断，主体称谓和责任边界清楚；
- 重点段落存在因果、递进或流程关系，不是连续的功能短句或表格释义；
- 复杂主题至少能指出一个当前项目对象、边界或验收口径，缺失时已暂停或标明占位；
- 没有连续重复“所投产品/平台支持……”，也没有连续重复“通过……实现……确保……”；
- 表格前后都有必要的正文解释，正文没有被表格完全替代；
- 固定表单、表头、列顺序、行粒度和签章区未被改写；
- 正式内容没有内部编号、研究提示、工作备注或模糊章节位置；
- “完全满足/无偏差”与已决定承诺一致，材料缺口已进入待补清单；
- 不存在虚构的人员、参数、时限、价格、证书、案例或验收结果；
- 偏差表和索引表的章节引用真实存在；
- 项目名称、主体名称、产品名称、数字、单位、术语和交付物跨章节一致；
- 正式 Markdown 可直接交给 `bid-backfill`，不需要回填阶段重新解释。

## 十、恢复路径与完成标准

| 问题 | 最小恢复路径 |
|---|---|
| 目录或填写目标变化 | 回 `bid-plan`/`bid-template`，下游内容重新处理 |
| 表格语义不清 | 回读底板和填写说明，只重做当前表 |
| 事实、材料或待补项变化 | 只修订受影响正文和后置表格 |
| 正文机制不足 | 在当前正式 Markdown 中补齐流程、控制、异常和验证 |
| 跨章节冲突 | 以事实基线和填写说明为准，同步修订受影响节点 |
| 发现无来源主张 | 删除、改为项目设计/验收目标，或使用明确占位 |

完成条件：所有可安全编写的动态节点都有正式 Markdown；固定表单和表格遵守模板语义；正文事实、设计、承诺和验收边界清楚；偏差/索引表引用真实章节；待补事项可追踪；正式内容可直接交给回填和独立终审。
