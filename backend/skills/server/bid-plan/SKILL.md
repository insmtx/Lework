# 投标响应规划

由招标需求与合规分析师主导，招标项目负责人组织确认，投标响应策略与内容主笔参与。目标是建立“每项招标要求应由哪一章、哪种证据和哪种填写方式响应”的可执行蓝图，而不是提前代写章节。

## 进入闸门与权威产物

进入前：输入冻结清单、规范 DOCX 信息、来源关系与预审结论、模板来源/章节边界确认均已存在。填写说明由后续 `bid-template` 建立。

| 产物 | 路径 | 作用 |
|---|---|---|
| 原子要求 | `work/招标/requirements.json` | 每项要求的来源定位、类别、强制性、评分/合同属性和响应义务 |
| 响应覆盖 | `work/招标/coverage.json` | 要求到目录、证据、固定表单或待补项的映射 |
| 事实基线 | `work/项目/bidder-facts.json` | 已确认的投标方、产品、项目事实及其来源 |
| 材料索引 | `work/项目/material-index.json` | 已提供证明材料和可用范围 |
| 待补清单 | `work/项目/pending.json`、`work/项目/待补充清单.md` | 未确认事项、影响和提交前是否必须补齐 |
| 最终目录 | `work/投标文件/目录.json` | 已确认的章节层级、顺序、叶节点与内容文件夹 |

## 执行流程

### Step 1：提取并闭合原子要求

从已冻结的正式来源逐条提取资格、商务、技术、格式程序、评分和合同义务。以正式文件中的独立小节、子项或表格行作为不可合并的来源单元：一个来源单元只生成一条要求记录，且该记录只保留一个来源条款定位。每一项必须表明：

- 是否强制、否决、评分、合同或仅背景信息；
- 要求投标方陈述、证明、填写表单、提供附件还是承诺执行；
- 所需事实/材料是否已经确认；
- 应进入目录正文、固定表格、附件还是待补清单。

不要把“评分项”当成独立响应类别；它是影响响应深度和证据优先级的属性。不要留下没有处置结果的语义来源单元。

### Step 2：建立事实、材料与待补边界

只从用户提供且可核验的材料提取投标方、产品和项目事实。将已确认值、来源和适用限制写入事实基线；把证明材料的名称、有效性和可支持的要求写入材料索引。

未知、冲突、过期、需签章或需用户确认的内容进入 `pending.json`，而不是临时写成肯定事实。随后生成 Markdown 视图：

```bash
python3 skills/bid-plan/scripts/generate_pending_view.py \
  --project-root "$PROJECT_ROOT"
```

待补项必须说明目标位置、影响、是否提交前必须补齐及不补的处理方式。日常可用待补占位不等于允许带着资格、报价、签章或法定否决项提交。

### Step 3：建立要求—响应覆盖关系

让每项需要响应的原子要求至少有一个可验证去处：目录章节、固定表单、资格附件、偏离表、报价表或待补项。覆盖关系必须说明“在哪里响应”和“用什么已确认事实或材料响应”；仅写“已覆盖”无效。进入商务或技术偏差表的要求，还必须登记唯一的偏差表类别、唯一的响应章节定位和唯一的偏差说明；不得将多个来源条款并列到一行。

优先处理否决项、强制格式、评分高权重项、合同实质条款和模板固定字段。若同一要求需要正文与表单双重响应，两处都要登记，不能用一处代替另一处。

### Step 4：设计最终目录与章节约定

目录应先服从招标固定章节和表单，再组织资格、商务、技术、实施、服务、培训、附件等实质内容。每个叶节点至少明确：标题、层级、顺序、对应内容文件夹、主要响应要求、是否关联固定模板目标和是否允许多 Markdown 文件。

不要为了工程化而给每章创建固定 JSON 合同。章节具体填写目标、素材边界和方法将由后续 `填写说明.md` 统一表达；本阶段只锁定目录和覆盖意图。

### Step 5：执行两个确认闸门

先向用户展示事实基线、重大待补项和冲突；用户确认后，将确认范围、例外和待补处理写入 `bidder-facts.json`、`pending.json` 和相关人工审阅视图。

再展示最终目录、固定章节处理方式和要求覆盖说明；用户明确确认后，将最终版本写入 `work/投标文件/目录.json`。目录文件即记录确认后的名称、层级、顺序与叶节点文件夹。

用户只修改局部时，最小范围修订相应产物，再重新展示确认版本。未确认目录不得进入模板制作或正文写作。

### Step 6：完成并交接

确认六项权威产物都已落盘后，交接给 `bid-template`：确认后的目录、模板来源与章节边界、事实边界和待补项。模板工程师据此识别固定表单和响应位置。目录变化时，先更新本阶段的覆盖关系和目录，再重新制作受影响的模板、正文和候选文件。

## 阻塞、恢复与完成标准

| 情况 | 处理 |
|---|---|
| 正式要求含义或版本冲突无法判断 | 标明来源和影响，阻塞并请求用户澄清；不得选择更宽松解释。 |
| 事实缺失 | 写入待补项并使用占位符；仅在影响资格、模板路线、目录或提交资格时阻塞。 |
| 目录与固定模板冲突 | 回到填写说明或模板路线处理，不擅自删除固定章节。 |
| 用户要求改已锁目录 | 从 `plan` 使下游失效，更新覆盖和目录后重新确认。 |

完成条件：每个实质性要求都有可追溯来源和响应去处；事实与待补边界清楚；覆盖关系无关键空洞；目录经用户确认且已锁定。
