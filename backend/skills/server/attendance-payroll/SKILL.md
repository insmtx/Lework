# 考勤核对

## 阶段路由

进入或跨越以下阶段时，先用 `scripts/workflow_gate.py` 检查当前任务的阶段证据和用户消息序列。只把对话中真实可见的用户原文及现有文件/回执摘要交给检查器；请求须带当前 `attendance.json` 路径，检查器自行计算其 SHA-256，并与 Review 摘要、版本及其在对话中展示后的用户消息序号核对。考勤确认记录必须回指同一任务中的明确确认消息，并与当前 Review 的月份、版本、摘要及人员范围完全一致；更正或重新生成 Review 后摘要/版本改变，必须重新确认。不得自造 `authorized=true` 或阶段成功记录。`ok=true` 仅表示符合正常 Skill 流程的准入条件，不是授权凭证，也不是 Runtime 强制权限。检查结果中的 `message_source_verified=false` 和 `runtime_enforced=false` 始终成立；文件路径与消息文本仍由 Skill 提供，写操作前 Agent 必须直接核对当前对话中的原始用户表达。无法确认消息来源或范围时停止。

**MCP 凭据安全：** Payroll 查询和写入一律通过当前 Runtime 已注册的受管 Payroll MCP 工具调用。严禁自行创建 HTTP/MCP 客户端、直接访问 MCP URL、读取或复制 Bearer Token/环境变量/Runtime MCP 配置，或把凭据放入 Python、Shell、JSON、日志、异常、Artifact 及聊天内容。若受管 Payroll MCP 工具不可用，停止并报告工具不可用；不得用临时脚本或手工 HTTP 请求替代。此规则约束正常 Skill 行为，不能阻止 Agent 绕过 Skill，也不能证明 Runtime 已将凭据对 Agent 隔离；不要把凭据写入任何任务文件。

人员候选只可来自当前 Task 实际调用 `resolve_payroll_person_candidates` 得到的完整响应；禁止手工填写 ID、从花名册推算人员 ID、重建候选证据或复用其他 Task/测试数据。保存当前完整请求和原始响应，核对响应覆盖全部当前 `record_id` 后再运行 `person_matches.py build`。该脚本的 SHA-256 仅绑定本地内容，不能验证响应来源；若无法直接取得当前 Task 的受管工具响应原文，应停止人员匹配。当前 Runtime 未向 Skill 脚本提供可验证的候选调用收据，因此 Skill-only 不能强制认证来源真实性。

阶段停顿规则：仅考勤任务首次完成考勤识别、核对表生成和 Artifact 声明后停止，不调用 Payroll MCP。原始请求明确包含 Payroll 处理意图时，首次确认前先只读获取当前 `list_roster`、准备全部项目候选；在**同一条助手消息**中交付当前考勤 Review、月份、人数、核对表、全部来源项目到 Payroll 项目的映射及待核事项；用户回复“确认以上考勤及项目对应关系”这类明确确认后，作为**一次第一确认**同时确认当前考勤 Review 和项目绑定，不得再分别追问“确认考勤”或重复确认同一映射。项目绑定脚本仍独立校验展示、映射和当前摘要，阶段门禁也须将同一确认消息绑定当前 Review。首次确认只让流程在原始 Payroll 任务意图明确时继续人员匹配及只读历史工资覆盖检查，不授权任何 Payroll 写入；只有考勤修订、项目映射变化或其他实质事实变化，才重新展示受影响内容并要求相应确认。进入一次性执行授权前，`workflow_gate.py` 必须从固定内部路径 `.attendance-work/payroll-readiness.json` 读取实际报告，并调用 `payroll_readiness.report_status()` 对照当前考勤、人员映射、月份及已选范围；报告状态、逐人明细、计数、规范化响应摘要和默认可核算范围还须与门禁请求一致。报告缺失、不可用、损坏、过期或冲突均停止。正式提交前仍须重新调用只读覆盖 MCP 并完成批次与范围复核。

完成映射与覆盖核验后，使用统一格式展示唯一默认可核算范围：标题“工资核算范围”，明确工资月份和“共 N 人”，用“纳入：”列出全部人员，用“排除事项：”列出每名未纳入人员及原因，并说明后续将正式提交考勤、执行正式预检查、通过后进行工资核算。范围摘要绑定该消息，再等待**一次第二确认**：用户明确按所展示范围开始工资核算，即授权该精确范围的完整正常流程。用户不必重复已展示的排除人员姓名或重新确认整份考勤；但排除项必须在最近一次范围展示中完整列明。授权通过后，同一授权仅可按顺序用于该精确范围的提交、Precheck 和核算；提交回执、`valid=true` Precheck、批次及范围校验仍逐阶段必需。用户授权若表达增加、排除或替换纳入人员等范围调整，不得按旧范围执行；先重新匹配、检查覆盖并按同一格式展示新范围，再取得一次新的执行授权，不新增授权阶段。输入摘要、映射、覆盖结果、月份、人员集合或批次变化均使授权失效。

考勤事实确认、身份/覆盖核验、执行范围展示与一次性工资核算执行授权各自有不同含义。只有在唯一范围已展示并明确说明将正式提交考勤、执行正式预检查、再进行工资核算后，用户明确表示按该范围开始工资核算，才进入一次性执行路径。`确认考勤`、人员匹配完成、覆盖检查通过、`继续处理`、`查看工资表` 或“可以核算吗”均不构成该授权；不得从含糊或否定表达推断授权。授权消息中如提出增加、排除或替换人员，必须停止并重新核定、展示范围。范围或证据改变后必须重新检查并展示。只要求生成考勤确认表的任务不得调用任何 Payroll MCP。覆盖报告的本地一致性复核不认证原始 MCP 响应的远端来源，也不认证用户消息；`ok=true` 不代表正式 Precheck 通过或远端数据未变化。

1. **上传与识别**：新任务首次进入时读取 [recognition.md](references/recognition.md)，按下面九步执行。每个 PDF 只做一次确定性预处理；每页至多读取一次布局概览和每个固定数据分区，不能临时增图或补认。预处理可对轻微整体倾斜执行有界自动纠偏，不得将纠偏结果描述为修复透视或局部变形。逐页观察后立即保存，并按人员行号绑定印刷汇总及备注。
2. **自然语言核对与修改**：用户要求查看、修改或确认考勤时读取 [attendance-review.md](references/attendance-review.md)。Agent 将明确的自然语言更正转成脚本 JSON 请求；目标或事实有歧义时只询问必要问题。每次修改后重新检查、导出最新核对表并重新声明该文件。
3. **Task 级项目绑定与人员身份匹配**：仅当原始任务包含 Payroll 处理意图时，在首次考勤核对确认前读取 Payroll `list_roster`，并把考勤月份、全部来源项目到精确 Payroll 项目的映射及完整考勤核对内容一并展示。按 `identity-matching.md` 的标准格式保存展示消息索引、原文摘要、月份、当前考勤 SHA、花名册响应 SHA、完整映射及规范化映射摘要；随后用户可用“确认以上考勤及项目对应关系”等简短明确表达一次确认全部映射，无需重复项目名称。`project_binding.py confirm` 同时校验助手展示与用户确认的顺序、消息角色/内容摘要、映射完整性和当前文件摘要。只要求识别并交付考勤表的任务不得调用 Payroll MCP，也无需建立项目绑定。把 `list_roster` 原始 JSON 保存到 `.attendance-work/payroll-roster.json`，调用 `scripts/project_binding.py prepare` 生成精确候选，再调用 `confirm` 生成 `.attendance-work/project-binding.json`。单项目、多项目均须完整映射；一个 Task 仅一个月份。不得使用静态别名、模糊匹配、历史项目映射或从 `roster_id` 推测 Payroll 人员 ID。之后仅当当前任务原始用户指令明确要求确认后匹配，或用户当前明确要求匹配时，读取 [identity-matching.md](references/identity-matching.md)。只调用 Payroll 的 `list_roster` 和 `resolve_payroll_person_candidates` 只读工具，并用 `scripts/person_matches.py` 构建或确认当前任务身份映射。脚本使用项目绑定中的规范项目筛查当前有效花名册，再要求候选响应明确证明唯一 Payroll 人员 ID 与该 `roster_id` 的关联；唯一且无已知关键冲突时自动匹配，即使考勤来源缺少公司或用工性质。岗位是软辅助字段，不单独阻断。原项目名保留为来源项目，确认后的 Payroll 项目名贯穿人员映射、历史覆盖、提交请求、核算和 Excel。异常候选继续走原有安全确认流程。候选接口仍可能执行历史证据查询，Skill 优化不代表服务端查询已减少。候选不等于可确认身份；展示完整候选信息后才接受用户明确选择。用户明确要求某条歧义身份记录暂不进入本次核算时，可另记绑定当前考勤/身份摘要和确认消息的范围排除证据；身份状态、候选、考勤人员记录均不改写，其他未解决冲突仍阻断。匹配或排除均不等于考勤确认或核算授权。
4. **历史工资覆盖与正式工资阶段**：只要求识别和交付考勤表的任务不得调用任何 Payroll MCP。工资流程意图明确且考勤已确认、身份映射完成后，读取 [payroll-processing.md](references/payroll-processing.md)，只读调用 `check_historical_salary_readiness` 并用 `scripts/payroll_readiness.py` 校验；默认候选仅为身份可靠且 `COVERED` 的人员。身份冲突先处理；未匹配、缺少历史、歧义、未知人员保留在排除原因中。展示月份、唯一人员范围、人数、排除事项以及正式提交/Precheck/核算的执行顺序，随后等待一次明确工资核算执行授权。通过 `PAYROLL_EXECUTION` 后，依次提交、核验提交回执、执行正式 Precheck、仅在 `valid=true` 时核算，并调用既有五 Sheet 导出器；不得自动缩围。覆盖结果、考勤或映射摘要变化、批次冲突、提交结果不明或 Precheck 阻塞时立即停止并重新核验/展示，不复用旧授权。固定 Task/Batch/Operation ID 规则不变。发现 Task ID 不构成授权；不向用户索取 Task ID 或 Batch ID。该授权是 Skills-only 的流程证据，消息来源未认证、不是 Runtime 权限；不能阻止 Agent 绕过脚本直接调用 MCP。

用户一次性工资核算执行授权覆盖该精确范围的正常完整流程：正式考勤提交、正式 Precheck、工资核算、工资表导出和 Artifact 声明。核算完整 `SUCCESS` 且成功提交/Precheck/核算回执均已核验、人员范围一致、`workflow_gate.py` 的 `PAYROLL_EXPORT` 准入成功、来源绑定校验通过时，不再询问是否生成工资表，直接调用 `scripts/build_payroll_workbook.py` 并声明其实际生成的文件。导出与声明不是新的写入授权点。不得为 `PARTIAL`、失败、结果不明或回执不完整的结果绕过准入或手工拼表。核算已成功但导出失败时，准确说明“工资核算已完成，但正式工资表导出失败”；不得误报核算失败或文件已交付。导出或声明重试只重试对应的本地导出/原文件声明，不得重新执行工资计算。文件生成、Artifact 声明成功和 UI 显示是不同事实。考勤确认表仅展示按 `record_id` 汇总的六列表人员数据和必要异常；逐日事实继续保存在原始 PDF、页级识别 JSON 和 `attendance.json` 中，不在正式 Markdown 生成每日矩阵或原始标记长表。Skills-only 内容比较不能证明本地文件确实由可信 MCP 产生。

用户在正式提交前更正考勤后，保留 PDF 与页级识别快照，只更新受控的 `attendance.json`，重新核对、导出并声明新的本地考勤 Review。以当前文件 SHA-256 判断事实版本；本 Skill 没有独立、可信的 Generation 计数器。SHA 改变后必须重新确认考勤、重新验证 Identity、重新执行历史工资覆盖检查、重新展示范围并取得新的执行授权；旧证据不得改写摘要后沿用。

如果正式考勤提交或工资核算回执已存在，新的本地 Review 仅表示本地更正，不表示 Payroll 已更新。正式写入前必须用当前 Task 固定的 `submit:<batch_id>` 与 `calculate:<batch_id>` 分别查询回执，并将查询状态传给 `workflow_gate.py`。任一状态未知、回执无法读取、已有提交/核算结果、或原提交事实无法与当前 Review 对齐时停止；不得重用旧回执、改 Batch ID、重提或重算。Payroll 当前没有经核实的提交修订/撤销或核算冲销/替代流程时，向用户说明需先由业务流程处理，不能把旧工资表交付为新考勤版本结果。新 Task 的 Task ID 不是“该月份无其他批次”的证明；无法核实其他批次影响时不进行正式写入。此门禁仅约束正常 Skill 路径，不能阻止 Agent 绕过 Skill 直接调用 MCP。

内部识别、候选和请求/响应文件统一保存在当前任务仓库的 `.attendance-work/`，识别视图保存在 `.attendance-pages/`。不要声明这些内部文件；只声明 `考勤确认表.md` 和已成功核算并实际生成的正式工资表。Artifact 收集会排除上述两个内部目录，但不会删除其中的文件。

## 新任务识别与交付顺序

按顺序完成以下步骤；内部命令无需逐项询问用户：

1. **PDF 预处理**：每个 PDF 调用一次 `scripts/pdf_prepare.py`。脚本为每页生成低尺寸整页布局概览和 1–3 张固定、高分辨率、全宽人员行带；概览加分区总数不超过 4。清单写入视图区域和 SHA。任务已有同源清单时预处理只复用缓存，不重画。
2. **单页视觉识别**：先读取一次概览，只判断表格/列布局，不从概览录入人员或考勤值；再按清单顺序各读取一次 `row_partition`。每行只从 `core_region` 所属分区录入，裁剪重叠只用于保留完整边界行。用原表印刷行号作为 `row_index`，不得按姓名合并同名人员。
3. **逐页 JSON 持久化**：综合本页固定分区，生成一份页级 JSON，保留 `row_index`、逐日原始标记、印刷出勤和行绑定状态；有冲突或不确定时写入警告。立即调用 `attendance_store.py save-page`；成功后进入下一页。失败时使用已读取视图修正 JSON，不重读图片、不覆盖已保存页。
4. **全页完整性检查**：全部页已观察并保存后调用 `attendance_store.py status`。缺失或无效页时停止并报告，不能组装正式工作数据。
5. **汇总工作数据**：仅当全部页有效时调用 `attendance_store.py assemble` 生成 `attendance.json`。
6. **考勤核对**：调用 `attendance_review.py check`；再调用 `attendance_diagnostics.py --workdir <工作目录>` 生成内部摘要。诊断不读取 PDF 或图片，也不进入正式产物。
7. **导出核对表**：调用 `attendance_export.py` 生成 `考勤确认表.md`。保留来源矛盾、未知状态、缺日和印刷值差异，不据此推算或覆盖原始事实。
8. **声明正式产物**：考勤表导出成功后，直接调用一次 `artifact_declare`，并在该次声明中提供正式路径、标题、MIME Type、Artifact Type 和 `is_final=true`；不得先声明 `is_final=false` 再依赖 Git Diff 兜底。只有响应 `ok=true` 才表示声明成功。
9. **简短回复**：说明识别范围、核对表生成/声明状态及需要用户核实的事项，然后停止。不得为写回复重新扫描 PDF。

Skill 能约束正常流程；`save-page` 校验行索引并拒绝覆盖已保存页级 JSON。现有 Runtime 没有按图片视图强制读取次数的技术闸门。不得声称已技术性杜绝任意工具或 Shell 重读。
正常识别不调用 OCR、视觉子代理或 Agent 自行裁图/生成补充图像；只读取清单内一次性生成的固定视图。

## 核对、修改和导出

工作数据只修改当前任务的 `attendance.json`，不修改 PDF 或逐页识别快照。通过稳定 `record_id` 定位人员；姓名不能用于合并同名人员。单项或批量修改均调用 `scripts/attendance_review.py apply`，再运行 `check`。脚本校验整批后一次写入。具体状态语义、输入格式和异常规则只在进入本阶段时读取 `references/attendance-review.md`。

导出当前版本：

```sh
python3 scripts/attendance_export.py --data <工作目录>/attendance.json --output <当前项目仓库>/考勤确认表.md
```

提出任何考勤操作方案前先核对 [attendance-review.md](references/attendance-review.md) 和 `attendance_review.py` 的实际操作契约。当前更正只支持逐日状态、确认实际出勤汇总和经用户明确确认的来源警告处理；不支持删除考勤人员。身份待核人员如只需不参与本次工资核算，应使用独立范围排除证据，不得引导用户删除考勤记录、修改 Payroll 花名册或原始 PDF。

核对表应保留必要待确认事项；缺日、未知状态、印刷值冲突、来源页警告或无法确定项目归属不得伪装成完整确定数据。Markdown 仅显示项目分组的六列表人员汇总和必要异常，不含逐日考勤章节、日期矩阵或原始标记长表。每日原始事实仍保留在识别和工作 JSON 中，不得因展示精简而删除、推断或弱化更正/统计/来源核验能力，也不得按姓名合并人员。

诊断摘要保存在 `.attendance-work/.attendance-diagnostics.json`，仅供内部排查；不要声明为 Artifact，也不要复制到最终 Markdown 或对话回复。预处理耗时来自脚本的单调时钟；模型推理耗时和 Agent 实际图片读取次数不可观测时保持 `null`。

## 正式产物交付

仅在导出脚本成功后继续：确认其返回的绝对路径确实存在、是普通文件且位于当前项目仓库内，然后调用 Lework `artifact_declare`：

```json
{
  "path": "<导出结果中的绝对路径>",
  "title": "<例如：2026年6月考勤确认表>",
  "mime_type": "text/markdown",
  "artifact_type": "file",
  "is_final": true
}
```

只有工具成功且返回 JSON 中 `ok` 为 `true`，才能说“考勤确认表已交付”。该正式声明必须在一次调用中设置 `is_final=true`，不能依赖 Git Diff 兜底替代声明。仅当工具明确表示声明尚未写入且错误可恢复时，才可原样重试一次；结果不明确时不得重复追加声明，应报告状态待确认。路径、文件不存在、项目仓库范围等确定性错误不得重试，应报告交付未完成。没有可用的 `artifact_declare` 时报告环境阻塞，不得只报文件名并称已交付。

区分三个事实：文件生成成功、`artifact_declare` 声明成功、前端实际显示卡片。工具返回 `ok=true` 只证明声明写入成功，不证明 UI 卡片已显示；只有观察到实际 UI 证据时才能声称卡片已显示。不得修改 Lework 产品代码来补足交付。

## 面客回复

默认用简体中文，简要说明识别月份、项目、人数/页数（仅限已核实）、核对结果、待确认异常摘要及核对表生成/声明状态，并提示下一步。不得在聊天中复制完整人员表、逐日矩阵、全部正常人员名单、JSON、路径、脚本名或内部错误码；详细人员和逐日事实在 `考勤确认表.md` 中。用户明确询问某人或某日期时，可只展示所需明细。未成功生成核对表或未成功声明产物时，明确区分“文件未生成”与“文件已生成但交付未完成”；不声称卡片已显示。考勤表交付后等待用户自然语言核对或确认，不自动开展人员匹配和工资核算。用户确认考勤后，只有当前任务原始指令已明确要求该后续阶段时才继续身份匹配及只读覆盖检查；否则等待用户提出。人员映射完成本身仍不授权工资核算。
