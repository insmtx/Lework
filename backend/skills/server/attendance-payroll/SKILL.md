# 外聘人员考勤工资核算

## 目标

使用三类带角色附件完成可追溯的工资核算：

- `roster`：人员底表，人员身份、项目和人员类别来源；可多份，不限制数量。
- `historical_payroll`：历史人工工资表，提取固定工资构成、月份公共规则和同月对比参考；可多份，不限制数量；不得把本 Skill 生成的「工资核算表」（含工资核算明细等五张表）当作历史工资表。
- `attendance`：当月签字考勤资料，识别实际出勤和请假信息；可多份，不限制数量。

工资规则是本 Skill 的固定内置规则，不要求用户上传规则文件。不得把模型估算结果直接当成工资金额。

## 工作流

1. 检查三类附件是否存在、可读且角色正确；保存文件名、页码/行号和解析警告。
2. 解析 `roster`，归一化姓名和项目名称；底表只用于补充人员信息和辅助匹配，不决定本次核算人员全集。
3. 解析 `historical_payroll`，按字段语义建立工资基准和月份公共规则；`基本工资`就是`岗位工资`，不得因为不存在“工资标准”字面列而判定基准缺失。历史“人工应发工资”用于与本次提交且成功匹配的历史工资记录对比。
4. 图片型 PDF 不能当文本读。先用 shell 调用 `scripts/extract_attendance.py` 按原始页渲成 PNG；当前这次任务用的就是多模态模型，直接看这些 PNG 识别考勤。要求得到紧凑 records JSON：顶层月份、项目、`holiday_dates`，每人姓名、`actual_work_days`（必填：该行最右「实际出勤」印刷数字）、`marked_work_days`（必填：该行格子里 `8`/`√`/出勤/加班的个数，不含「换」「休」）、`personal_leave_days`（只统计格子里的「事」或「事假」，没有则写 0）、病假/旷工。印刷天数必须与该行姓名对齐，禁止把邻行合计错抄到另一人。计算器会校验 `actual_work_days == marked_work_days`，不一致列入复核，工资仍按印刷实际出勤计算。禁止用整月天数减出勤、把周末/加班/休/换/调填进事假。不要输出 1-31 日正常出勤符号。把 JSON 写入 `.attendance-vision.json` 后再交给计算器。已经是图片的考勤可直接看图，仍须写入该 JSON 文件。
5. 解析 `attendance`，保留原始页/行证据，识别出勤、事假、病假、旷工、年假、调休和未识别符号。考勤无法识别或月份冲突时，才阻塞工资计算。
6. 以考勤和历史工资资料实际识别出的人员为主，先按归一化“姓名 + 项目 + 人员类别”严格匹配（姓名去空格和末尾括号备注）。严格匹配失败时，才在项目和用工类别约束内生成 OCR/错别字等模糊候选；仅唯一高置信候选可采用并标记人工复核，同分或低置信候选必须输出候选来源，不得强行匹配。
7. 基准缺失或工资构成不完整的人员进入 `review_exceptions`，按缺失分项处理，不阻塞其他人员；有完整或部分可用基准的人员继续计算已确认分项。
8. 未确认规则只跳过对应工资分项并写入复核说明，不阻塞该人员其他已确认分项的计算。
9. 逐项对比本次提交且成功匹配的历史人工结果，生成差异字段、金额差异和一致性状态。
10. 必须生成核算明细、工资基准缺失清单、异常/复核清单和 Excel 结果；即使只有部分人员可计算，也不得只生成分析报告而不生成部分工资表。本场景不要求生成分析报告文件，分析结论在最终回复中简要说明即可。若计算器跳过了系统生成的工资核算表，最终回复必须点名文件，说明未作为历史人工工资表，并提醒核对是否错传或漏传。

## 确定性计算器

先把考勤渲成可看的页图，由当前多模态模型识图并写出 JSON，再调用 `scripts/payroll_calculator.py`，不得由模型直接心算或编造工资金额：

```bash
python scripts/extract_attendance.py \
  --input <当月考勤1.pdf或图片> \
  --output-dir <项目工作目录>/.attendance-pages

# 查看脚本列出的 PNG，按页识别后写入：
# <项目工作目录>/.attendance-vision.json

python scripts/payroll_calculator.py \
  --roster <人员底表1.xlsx> <人员底表2.xlsx> \
  --historical <历史工资表1.xlsx> <历史工资表2.xlsx> \
  --attendance <项目工作目录>/.attendance-vision.json \
  --month 2026-06 \
  --output <项目工作目录>/2026年6月工资核算表.xlsx
```

`extract_attendance.py` 只做本地渲染，stdout 返回页图路径；不要把完整 JSON 当作超长工具参数传递。每份考勤一份 JSON。

三类 `--roster` / `--historical` / `--attendance` 均至少一份、不限制上限；多份人员底表按行合并，多份考勤 JSON 合并 records，月份互相冲突时才阻塞。

基础工作日按核算年月动态计算：当月天数减去周六日（调休上班日除外）和不重叠的法定节假日；考勤未返回节假日时，计算器使用已维护的官方日历回退。加班天数为实际出勤减基础工作日，按当月周末自然周数量封顶。识图结果必须包含每人的 `actual_work_days` 和顶层 `holiday_dates`，不再要求周末出勤日期数组。计算器成功 JSON 含 `statutory_holidays`、`base_workdays`；最终回复说明节假日时只列出这些法定假日期（周末落在假期内的日期也要写，例如端午 6 月 19–21 日），不要罗列当月普通周六日，也不要写成“周末日期”。
PDF 按原始页逐页识别，保持表格行和日期列的完整对齐；不再拆分人员行或左右日期列。

历史工资表可能没有项目和人员类别列，计算器会从文件名本身提取项目简称（年份前的前缀）和用工类别短语（如「某某外包」「劳务派遣」，或年月之后、人员/工资之前的供应商简称），不内置客户或供应商名单；「外包」「某某」与更具体的「某某外包」视为同一类约束。无法唯一匹配时进入复核清单。计算器若发现 `--historical` 指向本 Skill 生成的五表核算工作簿，会拒绝将其作为历史人工工资表：全部都是产物则命令失败；与人工历史表混传时忽略产物，写入人工复核事项，并在成功 JSON 的 `warnings` / `skipped_generated_historical` 中列出文件名。最终回复必须转述该警告，不能只写进 Excel。计算器生成的工作簿必须经过 xlsx Skill 的重算和公式错误检查后，才能调用 `artifact_declare`。

## 固定计算边界

系统应发工资为税前金额：

`岗位工资 + 调整后绩效工资 + 工龄工资 + 职称工资 + 施工补贴 + 话费补贴 + 计入应发的高温补贴 + 交通补贴 + 加班费`

- 事假只扣绩效，且只有识别到「事」/「事假」格子才计入事假天数；`8`/`√`/出勤/加班计出勤，`休`/`调`/`走`/`/` 为休息，`换`为已认可调休。周末缺口和加班日不是事假。没有事假标识则绩效发全额。`调整后绩效 = max(绩效标准 - 绩效标准 / 21.75 × 事假天数, 0)`；
- 历史工资未计加班费（加班金额、个数、标准均为空或 0）的人员视为一口价，当月不计算加班费，也不用岗位工资反推加班标准；
- 仅当历史加班金额、个数或标准大于 0 时才计加班费；通用加班日标准：`ROUND(岗位工资 / 21.75, 0) × 2`；
- 有特殊加班日标准时优先使用特殊标准；
- 可计薪加班天数：每个周六或周日实际出勤日期各计 1 天，同一周两天都出勤可计 2 天，最终封顶为当月周末自然周数量；不再要求用户选择工休制度；
- 超出计划的出勤只记为应休未休，不增加当月加班费；
- 话补仅在季度末月（3、6、9、12 月）发放一次：若同季度此前月份已有发放记录则不重复计入；否则优先当前季度话补列，缺失时可参考该人员最近历史金额；无参考金额必须列入人工复核；
- 有效年假和调休当前不扣工资；
- 高温补贴默认 6—9 月，是否计入应发以工资基准规则为准；
- 社保、公积金、个税、HR 公司扣款和最终实发不在范围内。

## 阻塞与人工复核

只有以下情况可以阻塞工资计算：

- 考勤文件无法读取或无法完成识别；
- 多份考勤资料的月份互相冲突；
- 完全没有任何可识别的考勤人员。

以下情况不得阻塞，必须部分计算并列入清单：

病假/旷工扣款、入离职分项折算、跨项目施工补贴分段、调休余额、正式高温政策、工龄晋档、机关偶发加班、同名无法唯一匹配或工资构成不完整时，不得猜测。只将对应分项列入复核清单，不得阻塞岗位工资、绩效、补贴等其他已确认分项。`换`表示已认可调休：该日不计工资、不计实际出勤，不列为未识别符号或人工复核事项。输出异常、证据和需要确认的问题。

输出工作簿的工资核算明细、工资基准、考勤汇总、历史工资对比和人工复核事项均须冻结首行表头。
